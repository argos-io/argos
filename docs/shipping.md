# 市场配置与物流接入

状态：市场灵活配置、主流物流协议接入及聚合平台优先已确认；具体契约、能力清单和适配器为讨论稿。更新：2026-11-08。

当前电商及物流随之移出第一期可行性 demo，本文保留为后续产品参考，暂停服务商和履约细节澄清，见 [ADR-0012](adr/0012-feasibility-demo-first.md)。

关联 [电商需求](commerce.md)、[插件生命周期](plugins.md) 与 [站点业务后台](business-admin.md)。本文未选择服务商、开通账号或实施集成。

## 1. 已确认边界

- 首版交易基线是单商家 B2C 实物零售，每个站点的商家所在地与销售目的地需灵活配置。
- 需要支持业界主流物流接口协议接入，具体首批服务商及适配范围待确认。
- 首版优先接入聚合平台，同时保留承运商直连扩展接口；不将预置全部直连适配器作为这一决定的含义。
- 物流能力通过插件扩展，构建时安装、运行时按配置启用；对应管理功能注册到交付站点业务后台。

市场可配置意味着不将地区组合写死到核心代码；具体可用线路由站点配置、供应商实际能力及商家服务账号共同决定。不能将“市场可配置”视为所有国家、币种、税费和服务商能力已经实现。

## 2. 市场与配送配置（建议）

| 配置 | 建议覆盖 |
| --- | --- |
| 商家资料 | 经营所在地、联系方式及业务默认配置 |
| 发货与退货地址 | 发货地址、退货地址、联系人和供应商要求的地址字段；首版是否多仓独立确认 |
| 销售与配送区域 | 允许销售或配送的国家、地区和区域分组，禁运或不支持区域的处理 |
| 物流账号与服务 | 已安装 provider、服务账号、可用承运商、配送产品及启用状态 |
| 运费策略 | 固定运费、按重量或金额等规则、免邮条件、供应商实时报价；具体首版策略待确认 |
| 包裹数据 | 重量、尺寸、单位、包裹类型及商品与包裹的对应关系 |
| 跨境扩展 | 需要时由适配器声明报关、商品申报及单据字段，具体支持范围待确认 |
| 相关交易规则 | 与支付、币种、税费和单据配置建立明确关联，不在物流插件中隐式替代这些领域 |

对已安装且兼容的适配器，账号、配送区域和规则可由运行时配置维护；加入新的适配器或修改其代码仍需构建发布。

## 3. 主流物流协议的落实方式

建议使用“统一物流业务契约 + 服务商适配插件”：内部对报价、发货、面单和追踪等能力建模，适配器按各供应商官方协议转换请求、认证、错误、状态和回调。承运商直连接口与聚合平台接口均可通过此方式接入。

聚合平台优先的接入顺序已确认。核心物流模型不绑定具体聚合平台，承运商直连接口保留在同一适配契约下；首版具体交付哪些聚合适配器，需要按能力、双平台兼容和实际对接条件继续选型。

这里的统一契约是本项目的插件接口，不是声称所有物流服务已经共享一种外部协议。已调研的官方接口涵盖 HTTP/REST 调用和轨迹推送；如具体业务需要其他协议，由相应适配器明确实现，不将未验证协议列为已支持能力。

### 官方参考与候选对象

| 对象 | 官方可查能力 | 对本项目的意义 |
| --- | --- | --- |
| [Shippo](https://docs.goshippo.com/shipments/shipments) | 通过始发地址、目的地址和包裹创建 shipment，获取可用报价 | 参考报价、地址和包裹契约；作为聚合接入候选 |
| [EasyPost](https://docs.easypost.com/guides/getting-started) | 创建 shipment 获取报价、购买并获取面单、返回追踪标识并通过 webhook 更新 | 参考从报价到面单和轨迹的流程；作为聚合接入候选 |
| [DHL Tracking Push](https://developer.dhl.com/api-reference/shipment-tracking-unified-push) | 提供物流轨迹推送，可基于追踪标识或相应账号场景订阅 | 说明轨迹接口可独立于报价、下单和面单；作为承运商接口候选 |
| [快递100官方文档](https://api.kuaidi100.com/document/apidocumentation) | 官方检索内容列出查询、订阅推送和电子面单等接口类别；本次全文抓取超时 | 国内聚合接入候选，需在适配前补充完整文档与能力验证 |

查阅日期：2026-11-07。上述为官方接口调研与候选对象，不代表选定供应商、已验证账户可用性、全线路覆盖或已完成集成。DHL 此处仅核实轨迹推送，不据此推定其该接口提供报价或面单。

## 4. 物流能力契约（建议）

| 能力 | 建议内容 | 必须明确的边界 |
| --- | --- | --- |
| 能力与服务发现 | provider 支持哪些操作、账号可用服务及输入要求 | 不能将某服务商部分支持表现为全部支持 |
| 报价 | 输入地址和包裹，返回服务、费用、币种、时效及有效期 | 商家向消费者收取的运费与购买面单的成本分别记录 |
| 创建运单与面单 | 创建发运请求、获取外部 ID、单号和面单 | 创建、购买、可打印与实际发货状态分别映射 |
| 取消与费用退回 | 申请取消运单或面单，查询结果 | 取消物流请求不自动等于费用已退或订单退款 |
| 轨迹 | 查询、订阅推送、事件归一化及异常处理 | 保留供应商状态与事件时间；内部映射可追溯 |
| 退货物流 | 退货运单或面单及轨迹 | 与退货验收、订单退款、补库存分别处理 |
| 跨境和附加能力 | 报关数据、单据、保险、揽收等按 provider 声明 | 不支持的能力显式说明，具体首版覆盖单独确认 |

每个适配器声明能力矩阵，业务后台据此提供配置与操作。不能用空返回或静默忽略参数伪装能力支持。可以按需组合追踪适配器与发货适配器，但映射关系需要明确。

## 5. 业务关联与运行维护（建议）

- 将订单行和数量、履约记录、包裹、运单、面单及轨迹记录关联，支持按明确规则处理部分发货。
- 记录 provider、账号、服务、外部对象 ID 和内部请求 ID，避免仅用单号匹配所有业务对象。
- 购买面单或创建运单超时时先核查外部结果，按 provider 能力实现幂等或防重；不能盲目重试造成重复付费。
- 回调与轮询更新共用事件处理规则，可去重、补查和恢复；轨迹事件乱序不应错误覆盖已确认事实。
- 切换市场或物流配置不改写已成交报价和历史发货记录；有在途包裹时保留其原 provider 关联和必要处理路径。
- 报价失败或线路不可用时，按站点规则阻止该配送方案或使用显式配置的替代方案，不静默选择零运费。
- 后台提供配置、连接状态、报价、面单、发货、轨迹、异常和维护入口；具体动作按已安装插件的能力与启用状态开放。
- 适配器在 Cloudflare 和 Node.js 验证其调用、回调、任务和文件处理，不能仅验证服务端 SDK 在一个平台可运行。

## 6. 候选验收

1. 为不同站点配置不同始发地与销售区域，不修改业务核心，按配置选择可用物流服务。
2. 已安装 provider 的账号和配送规则运行时可维护；新 provider 仍必须经构建交付。
3. 对支持完整流程的适配器验证报价、面单、发货、轨迹和约定退货流程；对仅支持部分能力的适配器验证正确的能力声明。
4. 验证多包裹或部分发货的数量与关联，面单重试不产生重复购买，重复或乱序回调不重复推进业务。
5. 停用或切换 provider 时存量运单仍按契约处理，历史记录可查询；不支持线路或能力有明确反馈。
6. 同一配置与适配器在两个运行目标通过约定流程，源码接手者可按说明配置其物流服务账号。
