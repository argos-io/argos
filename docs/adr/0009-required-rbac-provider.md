# 通过必需 RBAC 基础插件提供后台授权策略

用户选择方案 A：RBAC 作为每站业务后台必需基础插件，随后台自动安装并启用；核心保留统一服务端授权入口。随后确认支持预设角色模板、自定义角色、多角色权限并集及受保护的 `owner`，管理员可以创建角色并选择权限，首个管理员自动获得 `owner` 且禁止移除最后一位有效所有者。接受范围包括这些能力和职责边界，不包括完整角色模型或具体接口。

## 决策

核心保留身份和成员基础及服务端统一授权入口，RBAC 插件承担角色与权限管理及授权判定，作为后台必需授权提供者；业务插件通过核心授权契约接入，不直接依赖 RBAC 角色名称。权限声明、依赖能力和策略版本的具体契约继续细化。

角色管理提供预设模板与自定义角色，不采用只能分配固定角色的限制。只按角色授予权限：权限配置在角色上，成员通过分配角色获得权限，不直接给成员配置单项权限或个人可授予权限清单。拥有角色管理权限的后台成员控制普通角色的创建、修改、删除及权限配置，该管理权限本身也通过角色获得，可由非 `owner` 成员承担。不默认向所有成员开放，也不包含 `owner` 系统角色管理；具体模板、权限矩阵及角色管理保护规则继续设计。

一个后台成员可分配多个角色，有效操作权限取各角色权限的并集，适应兼任多项职责；站点边界、具体资源范围和业务状态校验仍适用，不因角色合并而绕过。角色撤销后按剩余有效角色重新确定权限，具体生效时点与一致性保证继续细化。

保留受保护的站点所有者 `owner` 系统角色，首个管理员初始化时自动获得，禁止移除最后一位有效所有者，避免站点因成员或角色变更失去所有者。成员停用、删除、角色解除及并发变更均需保持这一约束，具体并发机制继续细化。

同一站点支持多个 `owner`，现有有效所有者可向本站其他后台成员授予该角色；追加授予后原所有者仍保留角色，始终保留至少一位有效所有者。该决定支持多人共同管理，所有者之间的撤销权、自行退出及转移规则继续设计。

`owner` 自动拥有本站全部已注册后台权限，新增插件权限也自动获得，无需逐项手动授予；成员状态、插件启用、站点与资源边界及业务状态校验仍适用。此规则不将未知权限或授权故障视为可放行，也不允许执行未启用插件的业务操作。

这满足每个交付站点都有后台登录与授权、角色策略通过插件提供的边界。RBAC 在构建时自动纳入交付物，后台启用时联动启用并检查就绪状态；依赖期间拒绝停用，授权缺失或故障时不放行后台受保护操作。具体能力依赖和授权接口目前尚不存在，需要独立核心维护任务实现。

首个管理员初始化与邀请继续独立于访客用户管理插件；核心与 RBAC 的授权协作需保证这两个已确认流程可用。授权故障不能通过放宽权限恢复，具体部署侧恢复路径和工具待设计。

## 替代方案与待确认

未采用可选 RBAC 增强插件：它要求核心始终保留另一套基础授权，并维护策略切换和迁移。采用必需基础插件使角色策略集中在插件内，核心仍统一执行服务端检查。

未采用仅固定角色方案，以便站点管理员按实际分工创建角色和组合权限；具体授权管理边界仍需约束。

未采用成员只能分配一个角色的限制，避免每种兼任职责都必须另建组合角色。

未采用首个管理员也只使用普通角色的方案；保留受保护的所有者身份及最后一位有效所有者约束。

未采用对 `owner` 逐项维护权限的方案，保证其可管理新安装或升级后的业务能力；具体权限目录和升级校验仍需实现。

未采用仅一位所有者且只能通过转移更换的限制，允许现有所有者追加授予其他本站后台成员。

未采用普通角色定义仅由所有者维护的限制；由通过角色获得管理权限的成员控制普通角色。用户进一步明确只按角色授权，不采用个人可授予权限清单；本人业务权限上限方案也未被选定，不作为已确认限制。具体角色管理保护规则继续细化。

用户进一步要求完成设计，[RBAC 设计 v1](../rbac.md) 已补齐普通角色管理与分配范围、所有者撤销/转移、逻辑数据与 API、初始化/邀请、原子事务与撤权边界、升级恢复及 RB1–RB28 验收。这些是待整体评审的细化提案，不扩充本 ADR 已接受的规则，也未实施；业务数据范围、服务调用方和具体存储选型继续由相应模块契约承接。

本决策延续 [后台基础边界](0006-required-admin-optional-visitor-accounts.md)，并将 [依赖规则](0007-required-plugin-dependencies.md) 扩展至后台宿主必需的 RBAC 插件；不批准具体能力名称、包结构或存储方案。
