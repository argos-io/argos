# 用户管理与 CRM：模块边界和需求基线

状态：讨论稿。更新：2026-11-08。关联 [系统需求](requirements.md) 与 [电商需求](commerce.md)。

分期说明：当前优先验证可行性 demo，电商已延期；下文访客用户管理与 CRM 为原产品需求和后续设计参考。当前 demo 已确认不安装访客用户管理和 CRM，保留独立后台所需的最小真实认证与授权；具体范围见已确认的 [需求第 8 节](requirements.md#8-编码前的澄清进度与就绪条件)，不继续以完整客户运营规格阻塞 demo。

已确认首版需要标准用户管理，以及作为独立增强插件的 CRM；CRM 首版覆盖完整客户运营能力，并为销售管理保留扩展接口。客户运营方向已确定，具体业务流程、登录技术、身份服务商及数据契约仍待设计。

已确认每站必备后台成员登录与授权；面向访客的注册、登录和账号管理由可选用户管理插件提供。仅有企业展示与客服的站点可以不安装该插件。CRM 和电商均强制依赖用户管理，沿用自动安装、联动启用与停用保护规则；所有电商站点统一要求买家登录后才能下单，见 [ADR-0006](adr/0006-required-admin-optional-visitor-accounts.md) 与 [ADR-0007](adr/0007-required-plugin-dependencies.md)。

## 1. 基础能力与增强能力

建议用户管理独立可用，CRM 按需在构建时安装、在运行时控制是否启用。登录、账号维护和业务权限检查不依赖 CRM；CRM 提供客户关系运营能力，通过公开契约关联账号及业务数据。

| 层次 | 建议职责 | 与其他模块的边界 |
| --- | --- | --- |
| 后台成员基础能力 | 按后台配置开放 Google、微信网站扫码和邮箱一次性登录链接；首个管理员通过一次性凭据保护的初始化页面建立，后续成员经邀请、验证后加入 | 不依赖访客用户管理插件；凭据生命周期、渠道配置与具体权限契约待设计 |
| 访客用户管理 | 访客账号、登录身份、账号状态、基础资料、会话、账号恢复及对应后台管理 | 按需安装；提供访客身份契约，不承担后台成员授权、订单或销售流程 |
| 电商客户 | 购买主体、交易联系方式、地址、订单关联及成交快照 | 电商强制依赖用户管理，下单必须登录；购买主体由服务端登录身份确定，具体客户与账号关联模型待设计 |
| CRM 增强 | 联系人档案、来源、标签、分群、负责人、备注、跟进与业务互动视图 | 强制依赖并自动安装用户管理；关联基础账号及获授权的业务记录，不接管登录凭据或修改交易事实 |
| 销售管理扩展 | 线索、企业客户、商机、销售阶段、任务、报价和销售流程 | 后续可选能力；首版保留扩展接口 |
| 外部客服适配 | 客服入口、供应商配置及获授权的身份或业务上下文关联 | 外部客服身份不自动成为本地账号；获取订单上下文与执行退款分别授权 |

“增强用户管理”不应被实现为将所有 CRM 字段直接加到基础用户表。CRM 联系人可以没有登录账号；电商买家下单则必须登录。联系人、账号与交易客户仍分别维护数据归属，具体关联模型待设计。

## 2. 身份边界（建议）

- 区分管理平台操作者、交付站点后台成员、站点前台用户和服务调用方；分别定义身份与授权范围。
- 已确认首个管理员通过受保护的初始化页面建立，使用部署时提供的一次性初始化凭据并验证所选登录身份；后续成员经邀请、验证后加入。后台采用按配置开放的 Google、微信网站扫码及邮箱一次性登录链接，不依赖访客用户管理插件。前台自动注册不授予后台成员身份；凭据生命周期、渠道配置和邀请契约待设计，见 [站点业务后台](business-admin.md)。
- 后台成员的角色与授权由每站必需的 RBAC 基础插件提供，核心保留统一服务端检查入口；随后台自动安装并联动启用，独立于访客用户管理。具体角色模型待确认，不把后台角色直接用作前台会员等级或买家订单访问规则，见 [RBAC 设计](rbac.md)。
- 同一个自然人可以承担多个业务角色；这不表示账号、登录入口、会话或权限必须共享，也不预设一定使用不同数据库表。
- 访客账号由用户管理插件维护，后台成员由必备基础能力维护，交易客户由电商维护，联系人由 CRM 维护。通过稳定 ID 和显式关联连接，关联规则、去重和合并流程需要设计；不预设底层认证实现或数据表必须分开。
- CRM 联系人可以尚未绑定登录账号；电商买家下单必须关联当前登录身份。收集到邮箱不代表对该邮箱的所有权已验证，不能仅凭邮箱相同授予历史订单访问权或绑定账号。
- 修改联系方式、关联账号或合并联系人，不能改变订单归属、提升权限或修改历史成交快照。
- 首版不提供前台账号合并；CRM 联系人合并不等于账号合并，不能借此转移登录身份或订单关联。
- 用户停用、注销、联系人归档与订单数据处理是不同动作，分别定义业务规则；不以连锁删除实现账号注销。
- 本轮不确定跨站点统一账号、组织与团队、企业 SSO 或跨站点 CRM 的范围；当前需求不能被解释为默认允许跨站点共享客户数据。

## 3. 访客用户管理候选清单

首版前台登录方向已确认：Google、微信网站扫码登录加邮箱一次性登录链接。Google 和微信按各站点实际有效配置独立生效，可只开放其中一个或同时开放两者；未配置的渠道不开放。邮箱登录时，用户提交邮箱、接收邮件并点击其中的一次性链接完成登录。邮件发送服务、链接有效期与重发失效策略仍待明确。后台成员支持相同三类渠道，按后台配置及成员资格生效，具体要求见 [站点业务后台](business-admin.md)。

已确认前台用户首次完成身份验证、尚无对应本站账号时，自动创建账号并登录，无需先完成独立注册；该规则适用于已开放的 Google、微信网站扫码和邮箱一次性链接。已有绑定身份再次登录时复用对应账号，账号停用或注销按其生命周期规则处理，不能借自动注册绕过。提交邮箱或发起第三方授权本身不创建账号，必须完成身份验证后再处理。自动注册仅创建前台账号，不授予后台成员身份。

已确认一个前台账号允许绑定多种登录身份：用户登录后，验证并主动绑定 Google、微信或邮箱。绑定后，通过任一已绑定身份登录都解析到同一本站账号，访问该账号已有资料和订单；普通绑定将尚未归属其他账号的身份关联到当前账号，不另建账号，见 [ADR-0008](adr/0008-site-accounts-and-login-identities.md)。

已确认目标登录身份已绑定另一个本站前台账号时，拒绝绑定并提示使用原账号，首版不提供账号合并。即使用户能验证两个账号，也不在绑定流程中转移身份或合并两边的资料、订单和其他业务数据；两个账号原有关联保持不变。解绑流程另行明确。

配置生效需要同时约束登录入口展示与服务端发起登录的行为，不能只隐藏按钮。建议分别记录各渠道的配置与就绪状态，缺少或无效的配置给出原因；未配置微信不影响已配置 Google 的使用，反之亦然，也不因第三方渠道未配置而阻断已就绪的邮箱登录。具体配置字段、凭据引用、运行时更新和在途登录回调的处理待设计；Google 与微信是否分为独立适配插件尚未确定。

微信首版仅支持网站扫码登录，微信公众号内网页授权不纳入首版范围。微信渠道生效时提供网站扫码入口，未配置时不开放；具体微信应用准入、接口参数与账号配置在实施选型时核实。场景区分参考腾讯官方开发对接指南，首版范围来自用户确认。

建议用站点内稳定账号关联不同登录身份，仅凭相同邮箱不自动合并账号；具体身份唯一性、重复或并发绑定处理在接口设计中落实。对支持 OpenID Connect 的提供商，建议优先使用其标准身份认证流程；其他提供商按官方身份接口适配。OAuth 与 OpenID Connect 的区别及依据见本文参考部分，具体 SDK 与认证实现尚未选定。

| 范围 | 建议首版基线 | 仍需明确 |
| --- | --- | --- |
| 账号生命周期 | 已确认前台用户首次验证成功后自动创建账号并登录；启用、停用、恢复和注销流程待设计 | 重复回调与并发注册、账号停用后的业务影响及注销规则 |
| 认证与恢复 | 已确认按配置生效的 Google、微信网站扫码及邮箱一次性链接，允许主动绑定多种身份；目标身份已属于另一账号时拒绝绑定，首版不合并账号 | 微信接入配置、邮件服务、链接生命周期、解绑与恢复流程 |
| 会话与安全 | 会话到期、主动撤销、凭据或权限变化后的会话处理、登录失败控制、安全事件记录 | 设备管理及具体策略；后台成员认证另属必备基础能力 |
| 基础资料 | 账号稳定 ID、显示信息、可验证联系方式、修改记录 | 哪些字段必需；各字段由谁维护和可见 |
| 管理与授权 | 访客用户列表、搜索、账号状态管理、访客角色和权限、关键动作审计 | 访客角色范围及具体权限矩阵；后台成员的管理权限由基础能力提供 |
| 对外扩展 | 稳定 API、身份上下文、插件声明权限、账号变更事件 | 事件版本、数据访问授权和登录 provider 的扩展方式 |
| 数据交付与维护 | 资料导出、迁移映射、备份恢复和账号生命周期规则 | 具体数据保留规则及迁移时是否撤销会话 |

账号资料、CRM 标签与消费统计应分别有数据归属；用户管理不依赖电商或 CRM 才能使用。

## 4. CRM 首版客户运营范围

已确认首版覆盖完整客户运营，并为后续销售管理保留扩展接口。以下作为客户运营的功能覆盖清单，后续需细化每项操作、权限、数据更新规则及验收标准。

- 联系人档案与来源，包括未注册账号的联系人；支持获授权的自定义字段。
- 标签、筛选与分群，明确手工标签与从业务事件计算的分群。
- 负责人、备注、跟进任务与互动时间线，支持权限和操作追踪。
- 关联账号、交易客户、订单摘要和外部客服会话链接，界面按访问权展示数据。
- 导入导出、重复记录提示和受控合并；导入联系人不能直接创建已验证登录身份。
- 客户统计及沟通偏好；消费金额与退款汇总标注数据来源、币种和更新时点。

销售线索、商机、销售漏斗和预测归入后续销售管理扩展。营销群发、自动营销、积分权益和会员等级的首版范围仍需单独明确；账号管理中的权限角色与面向客户的会员等级应分别定义。

### 销售管理扩展接口（需求已确认，契约为设计建议）

首版应提供可扩展的客户运营基础，不要求先实现销售管理界面或流程。建议覆盖以下扩展点：

| 扩展点 | 建议契约 | 需要保持的边界 |
| --- | --- | --- |
| 客户引用与关联 | 稳定联系人 ID、客户关联查询及归档或合并通知 | 销售模块引用客户，不复制一套登录身份；合并规则可追溯 |
| 企业与业务关系 | 允许扩展企业档案、联系人角色以及客户与商机的关联 | 具体组织模型由销售扩展定义，不预先锁定一对一关系 |
| 业务字段 | 可声明字段类型、命名空间、校验、读写权限和迁移版本 | 扩展不得直接覆盖基础身份与交易字段 |
| 活动与事件 | 允许追加获授权的销售活动、订阅客户事件、补发及去重 | 销售阶段和状态由销售模块拥有；CRM 时间线只展示获授权的信息 |
| 工作台与 API | 客户详情页扩展区、动作与权限声明、可版本化 API | 销售权限与用户管理、退款等权限分别授予 |
| 生命周期 | 声明模块依赖、迁移、停用及历史数据读取策略 | 停用销售扩展不破坏基础客户运营、账号或交易数据 |

## 5. 插件依赖与生命周期（建议）

- 已确认 CRM 强制依赖用户管理；选择 CRM 时构建流程自动安装用户管理及其必需依赖，用户管理也可单独安装。运行时启用 CRM 时自动联动启用已安装的用户管理，检查配置与就绪状态；用户管理未就绪时不能将 CRM 标记为已启用。
- 已确认 CRM 启用期间拒绝停用用户管理，并列出 CRM 等已启用的依赖者；操作人需先停用依赖者，不自动联动停用 CRM。
- 已确认电商同样强制依赖用户管理，遵循自动安装、联动启用和停用保护规则；CRM 与电商共用用户管理时，任一依赖者仍启用都会阻止停用用户管理。
- 建议关联访客账号时通过用户管理的公开契约，不直接修改凭据、会话或权限表。安装用户管理依赖不等于给每个 CRM 联系人创建登录账号。
- 安装、升级和从构建产物中移除 CRM 都随构建发布完成；已安装 CRM 的启停是运行时操作，遵循 [插件生命周期](plugins.md)。
- CRM 与电商、客服通过可选适配连接。即使不安装电商或客服，用户管理和 CRM 的基础功能仍可工作。
- 客户视图通过获授权的查询或业务事件更新，事件有来源、稳定关联和去重规则；CRM 更新失败可重试，不阻塞支付或下单。
- CRM 可以维护业务摘要和索引，但订单、支付、退款事实以电商为准；更新事件可以补发，视图可按权限重建。
- 停用 CRM 后移除其页面、任务和扩展入口，保留基础账号和电商能力；其数据保留、导出与再启用恢复规则需明确。
- 基础用户管理被其他模块依赖时，应阻止直接卸载，或要求先完成可验证的替换与身份迁移。
- 两种运行目标均验证账号、授权、事件与恢复契约；不强制依赖我们的托管管理平台提供日常登录服务。

## 6. 候选验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| UC0 | 企业展示与客服站点不安装访客用户管理 | 后台成员仍可登录并管理获授权的内容与配置；站点不提供访客账号能力 |
| UC1 | 仅安装基础用户管理 | 通过已配置渠道首次验证成功时自动注册并登录，可完成约定的退出、恢复和资料维护 |
| UC2 | 账号停用、恢复或权限变更 | 按明确策略处理已有会话与访问权；不因缓存或旧会话绕过策略 |
| UC3 | 构建时安装 CRM，随后在运行时停用及重新启用 | 无需重新构建即可切换启用状态；基础登录和账号功能持续可用；数据和入口按已约定规则处理 |
| UC4 | 未注册的 CRM 联系人随后注册账号 | 验证身份与授权后建立关联；不能仅靠提交相同邮箱取得其他账号或历史订单的访问权 |
| UC5 | CRM 合并联系人或修改联系方式 | 不改变账号权限、订单归属或成交快照 |
| UC6 | 重复、延迟或漏接订单和客服事件 | 按幂等规则处理并可补齐，不重复计算；CRM 故障不阻塞交易 |
| UC7 | 普通用户或未授权插件请求客户档案、订单或账号管理 API | 对数据与操作分别执行授权，不能借 CRM 关联越权 |
| UC8 | 注销账号或导出 CRM 数据 | 按分领域规则处理账号、关系与交易资料；导出不包含登录密钥或会话凭据 |
| UC9 | 在 Cloudflare 与 Node.js 运行同一套源码 | 选定身份流程、权限规则与插件生命周期结果符合相同契约 |
| UC10 | 创建联系人、维护来源与标签、分群、分派负责人、记录跟进并查看授权的互动与消费摘要 | 完成客户运营闭环；可查询、导出和追溯，统计口径明确 |
| UC11 | 用最小验证扩展引用客户、添加销售活动与详情页扩展，再停用该扩展 | 验证扩展接口可用；基础客户运营、账号和订单继续可用；不要求实现完整销售管理 |
| UC12 | 在未安装访客用户管理的工程中选择安装 CRM | 构建阶段自动补齐用户管理依赖并记录版本；运行时启用 CRM 时自动联动启用用户管理并检查就绪状态 |
| UC13 | CRM 和用户管理已安装，用户管理配置无效或启用失败 | 启用 CRM 时报告用户管理的阻塞原因，CRM 不进入已启用状态；后台成员基础能力仍可用 |
| UC14 | CRM 启用期间请求停用用户管理 | 拒绝并列出 CRM，保留两个插件原启用状态；先停用 CRM 后仍检查其他依赖者及用户管理自身停用条件 |
| UC15 | CRM 与电商同时启用，先停用 CRM 后请求停用用户管理 | 仍拒绝并列出电商；用户管理不因 CRM 停用而绕过其他已启用依赖者的保护 |
| UC16 | 登录后提交订单，或会话失效后再次提交 | 有效登录时以当前身份确定购买主体，未登录或登录失效时拒绝创建新订单 |
| UC17 | 未登录时浏览商品和加入购物车，随后提交订单 | 浏览与加购无需登录，提交订单前要求登录；登录时自动合并匿名与当前账号购物车，同 SKU 数量相加并重新校验价格库存；匿名购物车不能授予其他账号订单或资料的访问权 |
| UC18 | 分别通过选定第三方提供商与邮箱一次性登录链接登录后下单 | 所选登录流程可建立站点登录身份，下单使用站点内账号；同一账号已绑定的身份共用账号及订单 |
| UC19 | 提交邮箱后点击有效登录链接，再重复使用同一链接或使用过期链接 | 提交邮箱本身不建立登录状态；有效链接可完成登录，重复使用或已过期链接不能用于再次建立会话；具体有效期按后续契约验证 |
| UC20 | 分别只配置 Google、只配置微信、同时配置两者或均不配置第三方渠道 | 各站点仅开放有效配置的渠道，入口与服务端发起登录的行为一致；未配置渠道不阻断其他已就绪渠道，均未配置时不展示第三方登录入口 |
| UC21 | 站点有效配置微信后，通过网站扫码完成授权登录 | 可建立站点登录身份并按规则下单；首版验收覆盖网站扫码，微信公众号内网页授权不计入已交付能力 |
| UC22 | 分别使用尚无对应本站账号的 Google、微信网站扫码和邮箱一次性链接身份完成首次登录 | 验证成功后自动创建前台账号并建立登录状态，无需独立注册；未验证、取消授权或无效链接不创建账号，且自动注册不授予后台成员身份 |
| UC23 | 已绑定身份再次登录，或同一身份的首次登录处理重复、并发执行 | 复用对应账号，不重复创建账号；已停用账号不能通过自动注册获得替代账号绕过限制，具体注销处理按后续生命周期契约验证 |
| UC24 | 账号已有订单，登录后验证并绑定另一种登录身份，再使用新身份登录 | 仍为同一本站账号，可访问其已有资料和订单；不因绑定新身份创建账号或转移订单 |
| UC25 | 未登录、未完成新身份验证、取消授权或提交无效绑定链接 | 不能完成主动绑定，原账号的身份关联与订单归属保持不变 |
| UC26 | 登录当前账号，尝试绑定已归属另一账号的身份，包括用户能验证两个账号的情况 | 拒绝绑定并提示使用原账号，不提供合并或跨账号转绑；两个账号的身份、资料和订单关联保持不变 |
| UC27 | 未安装访客用户管理插件时，已有具备成员管理权限的后台成员邀请新成员并分配权限 | 受邀者验证身份后可加入业务后台并使用获授权能力；前台注册与后台成员加入保持各自流程 |
| UC28 | 未安装访客用户管理插件时，后台成员分别使用有效配置的 Google、微信网站扫码和邮箱一次性链接登录 | 三类渠道均由后台基础能力提供，验证后仍检查成员资格和权限；未配置渠道不开放，前台自动注册不代替后台邀请 |
| UC29 | 全新站点未安装访客用户管理插件，操作者使用有效一次性初始化凭据并完成所选登录身份验证 | 可建立首个管理员；成功后初始化凭据失效，后续成员通过邀请加入；具体初始化异常场景见业务后台验收 |

## 7. 参考依据与待确认问题

OAuth 2.0 是授权框架，见 [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html)；OpenID Connect 在 OAuth 2.0 上提供用户身份认证，见 [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)。对支持 OIDC 的第三方优先采用其身份认证流程是本项目的设计建议，具体认证 SDK 尚未选定。上述规范查阅于 2026-11-07。

[Google 官方 OpenID Connect 文档](https://developers.google.com/identity/openid-connect/openid-connect)确认其登录认证支持 OIDC。[腾讯官方开发对接指南](https://main.qcloudimg.com/raw/document/product/pdf/1441_64308_cn.pdf#page=36)在微信授权登录部分区分网站应用、微信公众号网页授权与移动应用登录；此处只借用场景划分，不表示选择腾讯身份产品。查阅于 2026-11-07；微信开发者官方网页本轮未能读取，具体接入参数尚未核实。

认证、恢复和敏感操作的设计参考 [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)，会话更新、撤销及超时参考 [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。这些是实施设计参考，本文不声明已经完成安全验证。

CRM 功能命名参考 [HubSpot 官方联系人文档](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/contacts/guide) 展示的联系人、属性、对象关联和合并等概念；不代表采用其产品或复制全部能力。参考资料查阅于 2026-11-06。

已确认首版完整客户运营、销售管理保留扩展接口，以及构建时安装插件、运行时启停。访客用户管理按需安装，前台支持按配置生效的 Google、微信网站扫码登录及邮箱一次性登录链接，支持主动绑定多种身份；目标身份已属于另一账号时拒绝绑定，首版不提供账号合并。后台成员通过邀请加入，支持相同三类登录渠道并按后台配置开放，由必备基础能力提供。CRM 和电商均强制依赖用户管理，遵循自动安装、联动启用和停用保护规则。电商未登录可浏览和加购，提交订单前必须登录；登录时自动合并匿名与当前账号购物车，同 SKU 数量相加，沿用登录前当前币种统一重报价，缺价商品保留并阻止结算，重新校验库存，此规则不属于账号合并。匿名购物车在当前浏览器保存，账号购物车由服务端保存并可跨设备继续使用。默认匿名购物车保存 30 天、账号购物车保存 90 天，均从最后修改起计时，允许按站点配置，过期清理不影响历史订单。在途业务处理、启用失败恢复、购物车同步冲突处理与期限配置变更的生效规则及解绑流程仍待设计。插件安全性由注册操作人负责，系统按可信插件模型设计。客户运营操作与验收细节、营销能力范围、微信接入配置、邮件服务与链接生命周期、后台渠道配置和具体权限矩阵仍需细化；具体支付和物流渠道待明确。
