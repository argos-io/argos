# 插件安装、启用与生命周期

状态：已确认安装、启用与插件信任边界；具体生命周期契约为讨论稿。更新：2026-11-08。

关联 [系统需求](requirements.md)、[ADR-0002](adr/0002-build-time-plugins-runtime-enablement.md)、[电商](commerce.md) 与 [用户管理和 CRM](users-crm.md)。

## 1. 已确认边界

- 插件必须在构建阶段安装，随站点源码和构建产物交付。
- 安装时按插件声明递归补齐必需依赖，无需操作人逐个选择；CRM 强制依赖用户管理，安装 CRM 即自动将用户管理纳入构建，见 [ADR-0007](adr/0007-required-plugin-dependencies.md)。
- 电商同样强制依赖用户管理，沿用必需依赖自动安装、联动启用与停用保护规则；电商插件包粒度和内部依赖另行设计。
- 已安装插件可以在运行时控制是否启用；启停不需要重新构建插件代码。
- 启用插件时自动联动启用其已安装的必需依赖，并检查配置与就绪状态；启用 CRM 时自动启用用户管理，无需逐个操作。依赖未就绪时不能将依赖者标记为已启用；运行时不为此安装缺失代码。
- 停用仍被其他已启用插件必需依赖的插件时，拒绝操作并列出依赖者，要求先停用依赖者；不自动联动停用它们。CRM 启用期间不能停用用户管理。
- 新增插件、升级代码版本和从构建产物中移除插件，通过构建与发布完成。
- 运行时开关只控制构建中已有能力，不负责下载、安装或替换插件代码。
- 注册插件的操作人负责评估插件安全性；系统按可信插件模型设计，不提供插件安全审查或恶意代码沙箱隔离。
- 管理端可以按需求生成新插件；生成代码和构建安装属于管理端流程。站点交付物不执行代码生成，也不在运行时安装新插件。
- 交付站点包含独立业务后台，每个插件必须向后台注册对应管理能力；插件契约覆盖业务实现及后台扩展。
- 访客用户管理是可选插件；后台成员登录与授权是每站必备基础能力，不受该插件安装与启停状态影响，见 [ADR-0006](adr/0006-required-admin-optional-visitor-accounts.md)。
- 主题是一类插件，页面和视觉定制通过主题实现。操作人及其 agent 任务仅组装插件、创建或编辑插件与主题，不修改核心代码，详见 [主题与操作边界](themes.md)。

这一定义同时适用于 Cloudflare 和标准 Node.js。允许将直接调用插件作为运行时设计候选，不要求为了插件安全引入隔离执行环境；具体加载、调用和故障处理方式尚待设计。

## 2. 建议区分的状态与记录

| 信息 | 含义 | 变更方式 |
| --- | --- | --- |
| 安装清单 | 交付版本包含哪些插件、版本、依赖、契约和平台要求 | 构建生成，随发布确定 |
| 期望启用状态 | 维护者希望插件启用还是停用 | 通过授权的运行时管理操作更新 |
| 实际生效状态 | 插件当前是否可用，或处于切换、等待、失败状态 | 由运行时按依赖、配置和执行结果记录 |
| 生命周期记录 | 启停动作、配置版本、操作者、执行结果和失败原因 | 运行时持久记录与审计 |
| 迁移与业务数据 | 数据结构版本、业务记录及在途操作 | 按独立的迁移、业务及保留规则管理 |

这些是候选职责，不要求五张数据库表。具体存储和状态枚举在设计阶段确定。

已安装不代表已启用；开关设为启用也不代表配置或依赖已经就绪。对调用方应能说明实际状态和原因。

建议安装清单区分操作人直接选择与依赖引入的插件，记录依赖来源并固定解析后的版本。缺失依赖、版本冲突或循环依赖应给出明确错误，不产出缺失必需能力的可交付构建；声明格式与解析机制待设计。同一兼容依赖被多个插件引用时复用安装结果，不因移除一个依赖者就自动删除仍被其他插件使用的依赖。

首版完整数据导出并恢复到 Cloudflare 或 Node.js 已确认，见 [ADR-0010](adr/0010-customer-owned-hosting-and-portable-data.md)。持有站点业务数据、文件或恢复状态的插件需要相应版本的导出/恢复契约，不能因停用就遗漏仍保留的数据；从构建中移除后的数据归档也须有可读取方案。具体逻辑数据、文件校验、在途状态与兼容检查见 [交付提案](site-deliverable.md#8-客户账户托管与完整数据交付)。

## 3. 运行时控制建议

- 通过交付程序的开放 API 提供状态查询和授权启停能力；后台和托管管理端使用同一契约。
- 启用前校验插件存在、版本兼容、依赖已满足、配置有效，以及所需迁移已完成。
- 联动启用建议先解析完整必需依赖链，再按依赖顺序执行；已经启用的依赖复用现状。可选适配不因该规则被自动启用，调用方仍需满足受影响插件的启用授权。
- 联动过程返回各插件的实际状态及失败原因。缺失、配置无效或启用失败的依赖阻止依赖者进入已启用状态；已完成步骤如何保留或补偿、重试与中断后如何恢复，继续在失败恢复契约中设计。
- 启停操作可重试且可追溯；并发变更有冲突处理与版本控制。
- 停用前建议检查直接及间接的必需依赖关系，并与并发启用协调，避免检查后出现新的依赖者。拒绝停用时保留原启用状态；依赖检查通过不代表满足在途业务等其他停用条件。
- 不仅控制菜单显示，还要控制服务端业务入口、事件订阅、定时任务、扩展动作和新业务请求。
- 多进程或多实例需要约定状态传播与生效边界；维护接口返回结果应说明切换是否完成，不能仅写入一个开关就报告所有实例已停用。
- 请求或任务开始时记录所需状态与版本，对已开始的操作定义完成、取消或转入维护处理的规则。
- 停用不自动删除数据，重新启用不重复初始化或重复执行数据迁移；数据清理走单独的明确流程。
- 若存在预渲染页面、缓存和客户端资源，需定义其更新、访问与失效策略，不能只隐藏后台入口。

精确的生效时限、是否允许某些操作重启实例，以及接口和状态存储方案仍待确认。插件版本变化随发布完成，运行时启停不应被实现为隐式安装新版本。

## 4. 依赖与停用策略（建议）

| 场景 | 建议处理 |
| --- | --- |
| 必需依赖未安装 | 拒绝运行时启用并说明缺失依赖；通过工程变更、构建与发布补齐代码 |
| 必需依赖已安装但未启用 | 已确认自动联动启用；检查配置与就绪状态，依赖失败时不将依赖者标记为已启用 |
| 停用被其他启用插件必需依赖的能力 | 已确认拒绝停用并列出依赖者，要求先停用依赖者；不自动联动停用，原启用状态保持不变 |
| CRM 停用 | 关闭新运营操作、相关入口和任务；账号与交易继续按各自规则运行；记录保留及补数策略 |
| 客服停用 | 关闭客服入口与新服务调用；已有外部会话及第三方数据按供应商和站点约定处理 |
| 电商停用或切换支付渠道 | 区分停止新交易与完成存量交易；在途扣款、退款、回调及历史查询需要专门策略 |
| 停用持有在途业务的插件 | 可拒绝直接停用，或进入维护阶段；直到符合约定条件后再完全停用 |
| 从构建中移除插件 | 先满足依赖、迁移、在途处理和数据可读要求，再构建发布；移除代码不等于完成业务清理 |

“维护阶段”指只保留完成既有业务所需的受控能力，不继续接收新业务。是否采用这一状态及哪些插件支持，需要在业务契约中确认，不能由插件任意绕过停用状态。

已确认 RBAC 是后台必需基础插件，随后台构建时自动安装、运行时联动启用；被后台依赖时拒绝停用，授权缺失或故障时不放行受保护操作，见 [ADR-0009](adr/0009-required-rbac-provider.md)。这将必需依赖扩展到后台宿主，具体能力声明、就绪检查与恢复契约尚需实现，候选设计见 [RBAC 设计](rbac.md)。

RBAC v1 已提出唯一提供者、权限目录校验、部署指纹、后台独立就绪状态和部署侧恢复的完整建议；细节尚待整体评审，不代表现有插件注册器或双平台存储已支持这些能力。业务插件的权限声明、模板及授权提交边界按 [RBAC 核心契约](rbac.md#6-核心授权契约与业务接入) 接入。

## 5. 已确认的可信插件模型

已确认插件安全性由注册插件的操作人评估和负责。系统接纳注册后的插件为可信代码，不提供平台侧插件安全审查、恶意代码隔离或受限权限沙箱；不要求为此引入 Dynamic Workers 或 workerd 等沙箱运行环境。

插件 API、数据归属、依赖和生命周期约束用于可维护性、业务正确性与功能组装，不承诺阻止恶意插件绕过接口操作宿主资源。运行时启停同样是功能开关，不是安全隔离机制。

账号权限、退款授权、支付回调校验等属于交付站点自身的业务行为，按相应模块契约实现。处理插件报错、任务失败和数据迁移问题仍是运行时维护职责。具体决策见 [ADR-0003](adr/0003-operator-trusted-plugins.md)。

## 6. 后台扩展注册

已确认后台管理功能是插件组成部分。插件的菜单、管理页面或组件、操作与必要接口随构建交付，运行时按启用状态开放。通用后台不内置每个业务模块的专属逻辑。

建议通过统一注册契约声明插件标识、页面与路由、菜单、操作、配置与状态视图、业务权限，以及对其他插件管理界面的扩展。具体字段、前端框架和打包方式待设计，详见 [站点业务后台](business-admin.md)。

## 7. 候选验收

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| PL1 | 构建包含 CRM，但初始未启用 | 产物与状态可查询；CRM 业务未开放 |
| PL2 | 运行时启用、停用再启用已安装插件 | 不重新构建代码；入口与任务按约定切换；数据按规则保留 |
| PL3 | 请求启用构建中不存在的插件或版本 | 明确拒绝，不能转成运行时下载或安装 |
| PL4 | 多实例处理切换，并发或重复提交开关变更 | 状态可追踪，有冲突与重试规则；在约定时限内达到一致结果 |
| PL5 | 停用仍被已启用插件必需依赖的插件，或在迁移未完成时启用 | 拒绝停用并列出依赖者，迁移未就绪时不将插件标记为已启用；不留下可用状态下的缺失依赖 |
| PL6 | 停用支付相关能力时有待确认付款、退款或重试回调 | 先处理依赖与在途业务，存量交易不会因入口消失而遗失 |
| PL7 | 停用后通过旧链接、API、任务或缓存入口访问 | 按约定拦截或提供受控维护行为，不只隐藏菜单 |
| PL8 | 启停切换失败或执行实例重启 | 持久状态可恢复，失败原因可定位，不将半完成切换误报成功 |
| PL9 | 两种运行目标使用同一套插件与启停配置 | 安装清单可追溯，运行时语义和验收结果满足同一契约 |
| PL10 | 新插件注册对应后台管理能力后纳入构建 | 后台可呈现其管理入口与操作，无需修改通用后台的业务分支 |
| PL11 | 运行时停用插件后访问旧后台链接或提交管理操作 | 页面、操作和接口遵循同一启停契约；必要的存量维护行为按插件规则处理 |
| PL12 | 仅选择 CRM 后构建 | 自动安装必需的用户管理，记录依赖关系与最终版本；不要求操作人单独安装依赖 |
| PL13 | 所选插件经多层依赖引用同一兼容插件 | 递归补齐必需依赖并复用安装结果，可追溯依赖来源 |
| PL14 | 必需依赖缺失、版本冲突或出现循环依赖 | 明确报告依赖错误，不产出缺少必需能力的可交付构建 |
| PL15 | CRM 与用户管理已安装但未启用，只请求启用 CRM | 自动联动启用用户管理并检查就绪状态，随后启用 CRM；不要求逐个启用依赖 |
| PL16 | 联动启用时必需依赖配置无效或启用失败 | 报告具体依赖及失败原因，不将依赖者标记为已启用；实际状态可查询，恢复行为按后续契约验证 |
| PL17 | CRM 已启用时请求停用用户管理 | 拒绝并列出 CRM，两个插件保持原启用状态；不联动停用 CRM |
| PL18 | 一个插件被多个已启用插件必需依赖，仅停用其中一个依赖者后再请求停用它 | 仍拒绝并列出其余已启用依赖者；全部依赖者停用后仍检查该插件自身停用条件 |
| PL19 | CRM 与电商同时依赖用户管理，只停用 CRM 后请求停用用户管理 | 仍拒绝并列出电商；自动安装共用依赖不使它归某一个依赖者独占 |

上述候选验收还需补充平台和业务具体处理方式；不代表已经实现或验证。
