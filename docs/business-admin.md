# 站点业务后台与插件管理功能注册

状态：已确认独立后台交付、成员邀请制、插件注册与必需 RBAC 插件定位；demo 已确认普通邮箱邀请及链接登录，完整产品契约仍为讨论稿。更新：2026-11-09。

当前 demo 优先验证插件能注册后台功能、实际保存数据及执行服务端授权。完整成员和授权管理流程保留为产品要求，不要求先穷尽所有边界才验证插件机制；本期最小真实认证与基本授权范围已确认，见 [demo 范围](requirements.md#8-编码前的澄清进度与就绪条件)；本期认证渠道及契约执行基线见 [最小技术方案](demo-design.md)，后台采用 React、接入核心的薄 Astro/Hono 站点宿主，不以假登录、匿名管理 API 或仅隐藏按钮替代真实检查。

Q75 已确认 demo 的真实认证改为普通邮箱：邀请邮件中的一次性链接加明确确认完成邮箱验证及加入，日常登录也使用邮件链接，不要求 Google 账号。首个管理员仍须额外验证部署的一次性初始化凭据；普通登录不自动新增成员或授予角色。本期邀请发放保留部署侧受保护命令，不增加完整管理界面；链接过期、单次消费、用途与来源检查见技术方案。下文 Google/微信/邮箱三类渠道是保留的完整产品方向，不要求本期同时实现三类渠道。

关联 [站点交付物](site-deliverable.md)、[管理端](management-system.md) 与 [插件生命周期](plugins.md)。

## 1. 已确认要求

- 最终站点交付物必须自带独立业务后台，随站点源码交付。
- 业务后台独立于站点生成与管理端，为交付站点提供日常业务操作。
- 每个站点必备后台成员登录与授权，不依赖可选的访客用户管理插件；未安装或停用该插件不影响后台成员访问。角色权限矩阵及底层认证复用方式仍待设计，见 [ADR-0006](adr/0006-required-admin-optional-visitor-accounts.md)。
- 首个管理员通过受保护的初始化页面建立：使用部署时提供的一次性初始化凭据，选择并验证登录身份后创建管理员。初始化成功后凭据失效，入口不再用于创建管理员；后续成员遵循邀请制。
- 首个管理员初始化完成后，其他后台成员采用邀请制：具备成员管理权限的人发出邀请并分配权限，受邀者验证身份后加入。该流程由后台成员基础能力提供，不依赖可选的访客用户管理插件；前台自动注册不授予后台成员身份。
- 后台成员支持 Google、微信网站扫码和邮箱一次性登录链接，按后台实际有效配置开放，未配置的渠道不开放；登录入口与服务端发起登录遵循同一生效规则。渠道验证成功后，仍按成员邀请及授权规则检查资格和权限。
- 插件不仅提供业务功能，还必须向业务后台注册对应管理功能。
- 插件在构建阶段安装，运行阶段可以控制启用状态；这一边界同样适用于其后台扩展。

管理端生成新插件时，需要同时生成相应管理功能和注册声明，构建发布后在交付站点中使用。

初始化凭据仅授权首个管理员的建立，不代替对所选登录身份的验证，也不作为后续正常登录凭据。完成初始化前，持有有效初始化凭据的操作者选择已就绪的登录渠道并验证身份；初始化未完成不能把未验证身份记为管理员。一次性消费、初始化完成记录与并发控制需保持一致，防止重复开户。具体凭据生成与交付、有效期、渠道准备顺序、失败重试与恢复流程待设计。

已确认 RBAC 为后台必需基础插件，随后台构建时自动安装、运行时联动启用；角色与授权策略由插件提供，核心保留统一服务端授权入口及必需能力检查。后台依赖期间拒绝停用 RBAC，授权缺失或故障时不放行受保护操作。支持预设角色模板与自定义角色，管理员可以创建角色并选择权限；一个成员可分配多个角色，操作权限取并集，仍受站点、资源和业务状态约束。具体模板、权限矩阵、授权管理边界和故障恢复步骤仍待确认，见 [RBAC 设计](rbac.md) 与 [ADR-0009](adr/0009-required-rbac-provider.md)。

普通角色由拥有角色管理权限的后台成员控制，包括创建、修改、删除及权限配置，可由非 `owner` 成员承担。只支持按角色授予权限：先配置角色的权限，再给成员分配角色；角色管理权限本身也通过角色获得。不直接给成员配置单项权限或个人可授予权限清单，不默认向所有成员开放角色管理。具体保护规则见 [RBAC v1 第 5 节](rbac.md#5-默认角色与授权管理) 的完整建议，尚待整体评审，不能凭普通角色管理授权修改 `owner` 系统角色。

v1 提案将普通角色管理者视为可信权限管理员，可配置本人尚未拥有的普通权限；成员角色分配单独授权，但分配含管理权限的角色也具有较高授权能力。该提案未设个人权限上限，不能将其当作已存在的部门级受限委派；所有者相互撤销与转移、版本冲突、在途撤权和恢复语义同样见 v1，尚未整体接受。

已确认保留受保护的站点所有者 `owner` 系统角色，首个管理员自动获得，禁止移除最后一位有效所有者。支持多个 `owner`，现有有效所有者可向本站其他后台成员授予该角色，原所有者继续保留角色。`owner` 自动拥有本站全部已注册后台权限及新增插件权限，仍受成员状态、插件启用、站点与资源边界及业务状态约束。成员停用、删除或解除角色等操作均不得使站点失去最后一位有效所有者；具体并发保护契约、所有者撤销与转移规则待细化。

后台渠道配置契约、受邀者的识别与邀请匹配方式、邀请有效期与撤销、邀请者可分配的权限范围，以及成员停用与恢复流程仍待设计。前后台支持相同登录渠道，不预设共用应用凭据、会话或数据表；具体认证代码复用方式待实现选型。初始化、邀请和后台登录能力必须在未安装访客用户管理插件时仍可使用。

## 2. 通用后台与插件职责（建议）

| 部分 | 建议职责 | 应保持的边界 |
| --- | --- | --- |
| 后台宿主 | 布局、导航、路由承载、通用组件、身份与操作上下文、插件注册处理及状态展示 | 不硬编码商品、订单或 CRM 等每个模块的业务操作 |
| 插件业务实现 | 业务模型、查询、操作、事件、任务与数据迁移 | 业务规则由插件维护，后台 UI 和开放 API 调用相同业务规则 |
| 插件管理扩展 | 注册菜单、页面、表单、列表、详情、动作、配置及必要接口 | 与插件代码版本一起构建和交付，运行时按启用状态和业务权限开放 |
| RBAC 授权插件 | 角色、角色权限、成员角色、授权判定与对应管理页面；具体模型待确认 | 后台必需基础插件，使用核心成员与授权契约，不依赖访客用户管理 |
| 跨插件扩展 | 向其他插件已声明的详情区、工具栏或面板增加管理能力 | 显式声明依赖与扩展点，目标未启用时遵循可选适配规则 |

后台宿主可以来自运行时基础包或单独的管理基础模块，具体包边界待设计。独立业务后台是明确交付要求，不意味着把所有后台业务实现放入最小核心。

## 3. 候选注册契约

以下为设计建议，不是已经选定的代码接口。

| 注册项 | 建议内容 |
| --- | --- |
| 插件归属 | 稳定插件 ID、版本、管理扩展 ID 与依赖 |
| 导航 | 菜单、分组、标题、排序及关联页面 |
| 页面与组件 | 路由、列表、详情、表单、设置页及自定义管理组件 |
| 操作与 API | 查询、创建、修改、批量操作及业务命令；明确其业务服务与接口 |
| 业务权限 | 入口展示和操作所需的站点业务权限，与 API 授权语义一致 |
| 配置与状态 | 插件设置、依赖就绪情况、运行状态、错误及必要维护操作 |
| 扩展点 | 向其他插件的详情页、工具栏、面板或工作台贡献组件与动作 |
| 生命周期 | 启停、维护阶段、迁移与配置版本对管理入口的影响 |

管理 UI 的具体前端框架、自定义组件形式、通用表单生成和代码组织尚未选择。不要求所有管理界面只能由通用 CRUD 表单生成；商品规格、退款和客户互动等复杂操作需要合适的业务界面。

对于主要提供后台服务或 provider 适配的插件，对应管理能力可以是配置、连接状态和维护视图，不必为了注册要求创建无意义的业务列表。

## 4. 构建与运行时启停（建议）

- 构建时纳入插件业务代码、后台页面或组件、注册声明和必要接口，检查标识、路由及依赖冲突。
- 运行时启用插件后，按其依赖、配置和当前用户业务权限开放管理入口；注册声明与代码已经存在于交付物中。
- 启用插件时自动联动启用已安装的必需依赖；后台展示各插件实际状态及未就绪原因，依赖失败时不能把依赖者显示为已启用，见 [插件生命周期](plugins.md)。
- 停用仍被已启用插件必需依赖的能力时，拒绝操作并列出依赖者，提示先停用依赖者；不能只在界面禁用按钮，服务端同样执行依赖检查。
- 运行时停用时，处理菜单、页面访问、管理操作和对应服务端入口，不能只隐藏导航。
- 对支付等有在途业务的插件，可按已明确的维护策略保留存量交易视图和处理动作，完整停用条件由插件契约定义。
- 后台宿主在授权可用时保留插件状态查询和恢复操作入口；停用业务插件不应导致无法查看或恢复其状态。授权提供者本身故障时按 [RBAC 恢复契约](rbac.md#82-v1-建议恢复交付契约) 从部署侧恢复，不能依赖已经不可用的普通后台授权接口。
- 跨插件扩展跟随双方启用状态与依赖规则变化，不留下失效按钮或页面。
- 管理端调用开放 API 与站点业务后台操作，采用相同的业务状态检查和规则。

启停生效时限、缓存与多实例处理跟随统一插件生命周期方案，不在后台另建一套开关状态。

## 5. 首版插件管理功能示例

这些是对应业务范围的候选覆盖清单，操作细节继续随各模块需求澄清。

| 插件能力 | 对应后台管理示例 |
| --- | --- |
| 企业展示 | 企业资料、展示内容、媒体及已支持页面配置 |
| 主题 | 已安装主题、对应配置和兼容状态；主题源码的创建与编辑由内部管理端完成，业务后台不承担代码生成 |
| 外部客服接入 | 服务商配置、入口设置、连接状态；按对接能力提供会话或客户上下文链接 |
| 商品目录 | 分类、规格、变体、SKU、媒体、上下架和批量管理 |
| 订单、支付与库存 | 订单处理、支付状态、退款、库存调整与业务记录核对 |
| 市场与物流 | 商家和销售区域配置、物流账号与服务选择、运费规则、报价、面单、发货、轨迹与异常处理；按 provider 能力提供操作 |
| 后台成员基础能力 | 按后台配置开放 Google、微信网站扫码和邮箱一次性登录链接，提供渠道配置与就绪状态；后续成员经邀请、验证身份后加入并获得分配权限，具体邀请生命周期和权限矩阵待设计 |
| 访客用户管理 | 安装后提供访客用户列表、资料、账号状态及相应管理操作；支持查看和维护 Google、微信等登录渠道的配置与就绪状态，生效规则见 [用户管理需求](users-crm.md) |
| CRM | 客户档案、标签分群、负责人、跟进、互动记录、摘要和导入导出 |
| 后续销售管理 | 注册商机或销售流程界面，并向 CRM 客户详情增加销售扩展 |

## 6. 候选验收

- 交付站点在两种运行目标均提供业务后台，管理端不可用时仍能完成约定日常操作。
- 企业展示与客服站点未安装访客用户管理插件时，后台成员仍可登录并执行获授权的内容和客服配置操作。
- 全新站点未安装访客用户管理插件时，可凭部署时提供的一次性初始化凭据进入受保护页面，选择并验证登录身份，完成首个管理员建立。
- 缺少或无效的初始化凭据、所选登录身份未验证、重复或并发提交初始化请求时，不能创建未授权或重复的首个管理员；成功后旧凭据和初始化入口不能用于追加管理员。
- 首个管理员初始化后，具备成员管理权限的人邀请新成员并分配权限；受邀者完成身份验证后加入，仅获得分配的权限，未安装访客用户管理插件时也可完成该流程。
- 未安装访客用户管理插件时，后台已有成员分别通过已配置的 Google、微信网站扫码或邮箱一次性登录链接登录，按成员权限执行操作；未配置的后台渠道不开放。
- 未获邀请的前台用户自动注册、完成身份绑定或直接访问后台入口时，不因此获得后台成员身份；无成员管理权限的人不能发出有效邀请或分配成员权限。
- 新增插件仅通过其注册契约增加管理功能，无需修改通用后台的专属业务分支。
- 未启用插件的管理能力按规则关闭；通过旧链接、API 或页面中的旧动作也不能绕过启停规则。
- 根据权限呈现可操作入口；前台组件与服务端返回使用相同业务规则。
- CRM 向客户详情注册扩展，停用对应插件后不留下失效入口；后台仍可查询插件状态。
- 插件配置、代码和迁移版本不匹配时，后台清楚展示原因，不将不可用能力显示为可正常操作。

后台路由约定、UI 技术、具体组件与权限矩阵在实施设计阶段确定。
