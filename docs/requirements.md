# Argos 站点生成与管理：需求澄清稿

状态：讨论中；不是已批准的实施规格。更新：2026-11-07。

本文将用户已确认的要求与建议明确区分。待确认问题随访谈更新；确定存在重大取舍的架构决策后，再记录 ADR。

## 2. 系统边界

已确认有两套需求：管理端与最终站点交付物。源码优先、托管服务分离；生成站点或新插件属于管理端。两套独立需求分别维护在 [管理端需求](management-system.md) 和 [站点交付物需求](site-deliverable.md)，职责分离见 [ADR-0004](adr/0004-management-and-deliverable-boundary.md)。

| 部分 | 责任 | 仍需澄清的边界 |
| --- | --- | --- |
| 管理端：生成能力 | 理解需求、选择和复用插件、生成站点源码；允许生成项目插件并纳入构建 | 管理入口、生成任务、代码修改与验证、再生成策略？ |
| 管理端：管理与托管能力 | 管理站点及交付版本；调用 Cloudflare 平台能力部署，通过交付程序开放 API 维护 | 管理入口、维护操作范围、账户归属和升级流程？ |
| 最终站点交付物 | 源码、最小运行时、已选插件及独立业务后台；运行站点业务并提供开放 API；支持 Cloudflare 与标准 Node.js | 后台扩展契约、最小核心、平台适配和插件兼容如何实现？ |

上述前两行同属管理端的责任划分，不是增加第三套产品。管理端首版采用 Web 工作台和 agent 执行生成，可以集成 Codex 等成熟方案，部署不限定 Cloudflare。Cloudflare 与标准 Node.js 的运行兼容要求针对站点交付物；管理端自身的运行平台尚未确定。站点业务功能可以包含第三方服务调用，但这不意味着站点包含用于生成自身代码或新插件的 agent。

管理端永久仅限内部团队使用，不作为客户交付内容，也不规划客户自助使用阶段。客户通过站点业务后台经营站点；内部团队可以按服务约定使用管理端继续维护客户站点。客户自行修改源码后的版本，不要求重新接入管理端继续生成和升级；后台内容或配置维护不属于源码回流。管理端内部成员的身份与交付站点的用户、管理员和 CRM 客户分别定义。

已确认交付站点自带独立业务后台，插件负责注册相应管理功能。后台宿主提供通用框架，具体业务界面和操作由插件扩展；建议契约和验收见 [站点业务后台](business-admin.md)。

操作人及其 agent 任务仅编辑插件、主题和组装配置。核心系统通过独立仓库与核心维护流程演进，不按站点需求直接修改或分叉。页面和视觉需求落在主题，业务需求落在插件；详细边界见 [主题与操作边界](themes.md)，仓库职责见 [仓库结构](repositories.md)。

Cloudflare 平台 API 与站点开放 API 是两类接口：前者用于托管基础设施操作，后者由交付程序提供，用于站点维护。具体哪些动作归属哪类接口，需要在维护流程中逐项设计，不能假定站点开放 API 能直接替代构建、部署或基础设施配置。

同一套源码支持两个运行目标是已确认要求；采用不同入口、构建产物、环境配置和基础服务适配是候选实现方式。该要求不等于数据迁移已解决，数据库、文件存储、定时任务及插件依赖如何跨环境配置仍待设计。

建议让托管与用户自部署共用站点版本记录，外部调用方使用有文档、可版本化的站点开放 API。版本记录和 API 契约的具体形式尚未确认。已确认的交付边界见 [ADR-0001](adr/0001-source-first-delivery.md)。

## 3. 将“可维护”转化为可验收目标（建议）

- 接手者能在明确版本的环境里安装、启动和构建站点，知道核心、插件和项目定制代码分别在哪里。
- 依赖与插件版本可追溯；能判断升级是否兼容，以及需要迁移哪些配置和数据。
- 对仍由内部管理端维护的项目，后续生成和升级应保留其已有项目定制，具体机制待设计；客户自行修改后的源码版本回流不在要求范围。
- 发布失败时能识别失败版本并恢复服务；代码回退与数据恢复分别说明，不能假设恢复旧代码就能回退数据库。
- 站点的内容、文件、插件数据、配置和外部服务依赖有清单；密钥单独交接。
- 源码交付应能由用户在两种目标环境运行；完整数据导出、恢复和跨环境迁移的验收范围仍需明确。

以上尚未成为验收承诺；需先确定交付边界，再补操作步骤和可量化标准。

## 4. 插件生命周期：已确认边界与待设计规则

已确认插件在构建阶段安装，运行时控制已安装插件的启用状态。新增、升级及从交付产物中移除插件通过构建与发布完成；运行时开关不改变插件代码版本。此决策见 [ADR-0002](adr/0002-build-time-plugins-runtime-enablement.md)，状态、依赖和验收建议见 [插件生命周期](plugins.md)。

| 阶段 | 需要作出的产品选择 |
| --- | --- |
| 选择与安装 | 已确认构建时安装，安全性由注册操作人评估；插件来源、注册方式与版本管理待设计 |
| 组合 | 如何声明依赖、可选能力和冲突；两个插件争用同一路由时怎么办？ |
| 启用 | 已确认运行时可控制已安装插件是否启用；依赖检查、生效时限和多实例一致性待设计 |
| 运行 | 插件可以访问哪些数据、密钥和外部服务；失败后影响一个功能还是整个站点？ |
| 升级 | 新版本通过重新构建发布交付；核心和插件兼容性、迁移与恢复策略待设计 |
| 停用 | 页面、后台菜单、任务、API 和依赖该插件的其他功能如何处理？ |
| 卸载 | 默认保留还是删除数据；再次安装能否恢复？ |
| 替换 | 相同功能的不同插件能否互换；数据转换由谁提供？ |

已确认按可信插件模型设计：注册插件的操作人负责安全性评估，系统不提供插件安全审查或恶意代码沙箱隔离。依赖校验、配置校验、生命周期与故障恢复仍属于插件运行契约；业务模块的账号权限和交易校验按其自身规则实现。见 [ADR-0003](adr/0003-operator-trusted-plugins.md)。

## 5. 首版业务范围与验收场景

已确认首版提供企业展示模块、外部客服接入模块、电商模块组和标准用户管理；CRM 作为可选增强插件提供完整客户运营能力，为销售管理保留扩展接口。这里的“模块”表示业务功能范围；一个模块对应一个还是多个插件，尚未决定。提供这些能力与每个生成站点是否启用这些能力，是不同的范围。

| 模块 | 已确认 | 仍需澄清 |
| --- | --- | --- |
| 企业展示 | 首版必须包含 | 页面与内容范围；是否包含产品、服务、案例；内容由谁通过什么方式维护 |
| 客服 | 接入外部客服服务 | 服务商、访客入口、身份与订单上下文对接、数据归属及配置维护 |
| 电商 | 单商家 B2C 实物零售；市场灵活配置；国内与国际支付；主流物流接入，聚合平台优先；业务能力可拆分 | 市场配置规则、币种、具体支付与物流适配器、完整交易闭环与验收细节 |
| 用户管理 | 首版包含标准用户管理 | 账号生命周期、登录方式、资料、后台管理、角色权限及身份边界 |
| CRM | 独立增强插件；首版完整客户运营；为后续销售管理保留扩展接口 | 客户运营具体流程、营销范围、与电商和客服的关联，以及扩展契约 |

电商的候选模块、交易一致性要求和验收场景单独维护在 [电商需求基线](commerce.md)。电商能力通过插件扩展；最小运行时核心不因新增电商而默认内置订单、库存或支付业务模型。

商家所在地、销售目的地等按站点配置，具体服务范围由所启用的业务规则及供应商能力共同决定。主流物流接口以统一业务契约和物流适配插件承接，候选设计与官方参考见 [市场与物流](shipping.md)。

用户管理与 CRM 的建议职责、数据归属、插件依赖和验收场景维护在 [用户管理与 CRM](users-crm.md)。CRM 增强基础用户模块，不应成为登录、下单或支付的强制依赖；这属于待确认的设计建议。

此前提出的博客、联系表单只是访谈示例，尚未纳入首版需求。

以下是基于已确认模块的候选验收场景；具体操作步骤待模块细化后补齐。

1. 生成包含企业展示和客服入口的站点，交付源码；另一位开发者接手并修改展示页面。
2. 相同需求选择托管交付，维护者更新企业展示内容；插件升级后保留这些修改。
3. 为已有站点增加一个功能，检查是否只需添加插件和配置，是否需要改核心。
4. 停用客服相关插件后，企业展示仍按约定运行，客服入口有明确处理；若插件存储数据，需验证其保留和导出规则。
5. 一个插件依赖另一个插件时，阻止不兼容的卸载或提供明确的替代处理。
6. 插件升级涉及数据库变更，演示失败后的恢复过程并说明是否会丢失新数据。
7. 同一份交付源码分别在 Cloudflare 和标准 Node.js 部署，并验证所选业务功能及站点开放 API。
8. 完整数据迁移的候选验收：将托管站点数据迁出，恢复到用户自部署环境；具体迁移保证尚待确认。
9. 按选定交易模式验证商品管理、购物、下单、支付、履约、售后及运营管理闭环，包含并发、重复回调和故障恢复；详见电商需求基线。
10. 用户管理独立运行；可选安装或停用 CRM，并验证用户、订单、客服和 CRM 数据的访问权限与关联规则。
11. 构建时安装插件后，在不重新构建的情况下控制其启用状态，验证服务端入口、页面、后台入口和任务按规则生效；未安装的插件不能通过运行时开关启用。
12. 管理端不可用时仍可登录交付站点的业务后台，管理已启用插件的业务；新增插件注册其管理功能，无需向通用后台核心添加专属业务分支。
13. 生成任务产出可预览版本后等待操作人选择继续修改、交付源码或正式发布；选择与相应源码、构建结果和版本关联。
14. 按需求组装、生成或编辑插件及主题后，可构建站点及对应业务后台；核心源码无改动，缺少扩展契约时报告能力缺口。

| Q9 | 核心最小职责、插件协议、依赖和数据生命周期如何落地？ | 在上述需求明确后设计 |
| Q10 | MVP 边界、验收标准和实施切片？ | 在上述需求明确后制定 |
| Q11 | 站点开放 API 覆盖哪些维护动作；谁能调用；怎样授权、升级和扩展？ | 已确认必须提供开放 API；契约范围未讨论 |
| Q12 | 首版客服属于外部客服接入、自建人工客服、AI 客服还是组合？ | 已确认：A，接入外部客服 |
| Q13 | 首版电商以哪种交易模式和商品类型为基线？ | 已确认：单商家、B2C、实物商品 |
| Q14 | 电商的销售市场、结算币种、支付渠道和税费处理范围？ | 已确认市场灵活配置，不固定商家所在地与销售目的地；币种、支付和税费规则待细化 |
| Q15 | CRM 首版侧重客户运营、销售管理还是两者？ | 已确认：完整客户运营，销售管理保留扩展接口 |
| Q16 | 用户管理包含哪些身份与账号能力、登录方式和管理权限？ | 已确认标准用户管理；具体能力待细化 |
| Q17 | 插件安全性由谁负责，是否需要承载不受信任代码？ | 已确认：注册操作人负责评估，系统按可信插件处理，不提供安全审查或恶意代码隔离 |
| Q18 | 生成器只组合现有插件，还是可按需求生成项目插件？ | 已确认允许生成；由管理端完成，不由最终站点交付物完成 |
| Q19 | 站点内容、商品、订单、用户与 CRM 的日常业务后台是否随源码交付？ | 已确认必须提供；插件向业务后台注册对应管理功能 |
| Q20 | 管理端首版采用 Web 工作台、CLI 或现有编程 agent 作为主要入口？ | 已确认 Web 工作台加 agent 执行生成；成熟 SDK 可选，Codex 为候选；部署不限定 Cloudflare |
| Q21 | 管理端供内部操作人使用，还是面向客户自助使用或交付？ | 已确认永久仅供内部团队使用，永远不交付客户，也不提供客户自助入口 |
| Q22 | 客户修改交付源码后，是否需要支持内部管理端重新接入并继续生成和升级？ | 已确认不需要支持；保留交付源码独立可维护及内部托管项目持续维护要求 |
| Q23 | 主流物流首批适配优先覆盖聚合平台、承运商直连还是两者？ | 已确认：聚合平台优先，保留承运商直连扩展接口；首批名单待选 |
| Q24 | 首版支付需覆盖国内渠道、国际渠道还是两者？ | 已确认两类都覆盖，通过可选插件接入；具体首批渠道及能力待选 |
| Q25 | 管理端生成完成后由操作人选择交付或正式发布，还是自动发布？ | 已确认：agent 自动生成、修复、构建验证并准备预览，由操作人选择继续修改、交付或正式发布 |
| Q26 | 站点前台页面与视觉如何定制？ | 已确认通过创建或编辑主题实现，主题属于插件；操作人及生成任务不修改核心 |
| Q27 | 设计、核心和插件仓库如何组织？ | 已确认三个并列的独立仓库：argos（保留设计）、core（核心系统）、plugins（插件与主题），各自独立管理 Git 历史 |
