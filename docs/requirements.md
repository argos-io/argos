# Argos 站点生成与管理：需求澄清稿

状态：讨论中；不是已批准的实施规格。更新：2026-11-09。

本文将用户已确认的要求与建议明确区分。待确认问题随访谈更新；确定存在重大取舍的架构决策后，再记录 ADR。

当前优先级已调整：第一期是验证系统可行性的 demo，电商移出本期，不再继续逐项澄清电商细节。下表此前的“首版”业务要求作为后续产品目标保留，不代表必须全部完成才能开始 demo；最新分期见 R76–R77、[ADR-0012](adr/0012-feasibility-demo-first.md) 和第 8 节。

## 1. 产品目标与已确认需求

根据用户要求生成一套站点，按需组装功能，并在交付后保持可维护、可扩展。

| R39 | 电商强制依赖用户管理，沿用必需依赖自动安装、联动启用和停用保护规则；购买登录要求见 R40 | 第二十四轮确认：A |
| R40 | 所有电商站点统一要求买家登录后才能下单，不提供访客购买或按站点开放未登录购买的配置 | 第二十五轮确认：B；登录拦截位置见 R41 |
| R41 | 未登录可浏览商品和加入购物车，统一在提交订单前要求登录 | 第二十六轮确认：A；登录时自动合并购物车见 R71，合并币种见 R72，保存及跨设备范围见 R73 |
| R42 | 首版前台用户登录采用 OAuth 第三方登录加邮箱登录 | 第二十七轮澄清；邮箱方式见 R43，第三方渠道见 R44，身份绑定见 R47，后台登录渠道见 R50 |
| R43 | 邮箱登录采用邮件中的一次性登录链接，用户点击链接完成登录 | 第二十八轮确认：C；邮件服务与链接生命周期待设计，首次登录注册见 R46 |
| R44 | 首批第三方登录支持 Google 和微信，按各站点实际有效配置独立决定生效渠道；不要求每站同时开放两者 | 第二十九轮确认；微信场景见 R45，具体配置契约待明确 |

| R46 | 前台用户首次通过已开放渠道完成身份验证、尚无对应本站账号时，自动创建账号并登录，无需先完成独立注册 | 第三十一轮确认：A；适用于 Google、微信网站扫码与邮箱一次性链接，不适用于后台成员开户 |
| R47 | 一个前台账号允许绑定多种登录身份；用户登录后验证并主动绑定 Google、微信或邮箱，使用任一已绑定方式登录都共用账号及订单 | 第三十二轮确认：A；目标身份已绑定其他账号时见 R48，解绑规则待设计 |
| R48 | 目标登录身份已绑定另一个本站前台账号时，拒绝绑定并提示使用原账号；首版不提供账号合并，两个账号的身份与业务数据保持不变 | 第三十三轮选择更正：A |
| R49 | 首个管理员初始化后，其他站点后台成员采用邀请制：具备成员管理权限的人邀请并分配权限，受邀者验证身份后加入 | 第三十四轮确认：A；初始化见 R51，具体邀请契约待设计，登录渠道见 R50 |

| R51 | 首个管理员通过受保护的初始化页面建立：使用部署时提供的一次性初始化凭据，选择并验证登录身份后创建管理员；成功后凭据失效，初始化入口不再创建管理员 | 第三十六轮确认：B；凭据交付、渠道准备、有效期与失败重试细节待设计 |
| R52 | 设计 RBAC 插件并评估基于插件实现角色与权限管理的可行性 | 第三十七轮设计请求；插件定位随后由 R53 确认，默认角色及具体授权契约待设计 |

| R54 | RBAC 支持预设角色模板与自定义角色，管理员可以创建角色并选择权限，不限于分配固定角色 | 第三十九轮确认：A；多角色规则见 R55，具体模板、权限矩阵与授权管理边界待确认 |
| R55 | 一个站点后台成员可以分配多个角色，有效操作权限取各角色权限的并集；仍须满足站点、资源范围及业务状态校验 | 第四十轮确认：A；不因此授予跨站点或超出业务资源范围的访问权 |
| R56 | RBAC 保留受保护的站点所有者 `owner` 系统角色，首个管理员自动获得；禁止移除最后一位有效所有者 | 第四十一轮确认：A；权限范围见 R57，多所有者与追加授予见 R58，转移规则待确认 |
| R57 | `owner` 自动拥有本站全部已注册后台权限，新增插件权限也自动获得，无需逐项手动授予；仍遵循成员状态、插件启用、站点与资源边界及业务状态校验 | 第四十二轮确认：A；不允许执行未知权限或未启用插件的业务操作 |
| R58 | 同一站点支持多个 `owner`，现有有效所有者可向本站其他后台成员授予该角色；始终保留至少一位有效所有者 | 第四十三轮确认：A；追加授予不撤销原所有者，所有者撤销与转移规则待确认 |
| R59 | 普通角色的创建、修改和删除可以授权给非 `owner` 后台成员，不限定由所有者操作；角色管理须遵循相应权限和保护规则 | 第四十四轮确认：B；授权方式由 R60 进一步明确，不包含 `owner` 系统角色管理 |
| R60 | 只支持按角色授予权限：权限配置在角色上，成员通过角色获得权限；普通角色由拥有角色管理权限的后台成员控制，角色管理权限本身也通过角色获得 | 第四十五轮用户澄清；不直接给成员授予单项权限，不维护个人可授予权限清单；具体角色管理保护规则待细化 |
| R61 | 在已确认纯角色授权基础上继续完成 RBAC 插件设计，补齐可整体评审的规则与技术契约 | 第四十六轮设计请求；v1 细化规则为提案，不等于逐项接受或授权实施 |
| R62 | 继续收敛首版可交付功能与验收清单，以及托管、数据导出和恢复的责任边界 | 第四十七轮推进请求；具体业务清单与运维细节为候选，不自动批准全部功能 |
| R63 | 首版支持完整数据导出，并可恢复到 Cloudflare 或 Node.js，不仅保证同平台备份恢复 | 第四十八轮数据交付确认；导出范围、恢复流程与验收提案见站点交付物第 8 节 |
| R64 | Cloudflare 托管使用客户自有账户，由客户授权团队代管 | 第四十八轮账户归属确认；具体授权方式、费用及运维责任继续细化 |

| R66 | 首版同一个电商站点支持多种交易币种，商品可维护多币种价格，订单可使用不同币种付款；不限定每站仅一种交易币种 | Q59 确认：B；价格来源见 R67，单笔订单币种见 R69，展示换算及服务商结算币种待细化 |

## 2. 系统边界

已确认有两套需求：管理端与最终站点交付物。源码优先、托管服务分离；生成站点或新插件属于管理端。两套独立需求分别维护在 [管理端需求](management-system.md) 和 [站点交付物需求](site-deliverable.md)，职责分离见 [ADR-0004](adr/0004-management-and-deliverable-boundary.md)。

| 部分 | 责任 | 仍需澄清的边界 |
| --- | --- | --- |
| 管理端：生成能力 | 理解需求、选择和复用插件、生成站点源码；允许生成项目插件并纳入构建 | 管理入口、生成任务、代码修改与验证、再生成策略？ |
| 管理端：管理与托管能力 | 管理站点及交付版本；经授权代管客户自有 Cloudflare 账户，通过交付程序开放 API 维护 | 管理入口、授权接入、维护操作范围、费用和升级流程？ |
| 最终站点交付物 | 源码、最小运行时、已选插件及独立业务后台；运行站点业务并提供开放 API；支持 Cloudflare 与标准 Node.js | 后台扩展契约、最小核心、平台适配和插件兼容如何实现？ |

上述前两行同属管理端的责任划分，不是增加第三套产品。管理端首版采用 Web 工作台和 agent 执行生成，可以集成 Codex 等成熟方案，部署不限定 Cloudflare。Cloudflare 与标准 Node.js 的运行兼容要求针对站点交付物；管理端自身的运行平台尚未确定。站点业务功能可以包含第三方服务调用，但这不意味着站点包含用于生成自身代码或新插件的 agent。

管理端永久仅限内部团队使用，不作为客户交付内容，也不规划客户自助使用阶段。客户通过站点业务后台经营站点；内部团队可以按服务约定使用管理端继续维护客户站点。客户自行修改源码后的版本，不要求重新接入管理端继续生成和升级；后台内容或配置维护不属于源码回流。管理端内部成员的身份与交付站点的用户、管理员和 CRM 客户分别定义。

已确认交付站点自带独立业务后台，插件负责注册相应管理功能。后台宿主提供通用框架，具体业务界面和操作由插件扩展；建议契约和验收见 [站点业务后台](business-admin.md)。

每个站点的后台成员登录与授权属于必备基础能力，不依赖可选的访客用户管理插件。仅提供企业展示和客服的站点可以不安装访客账号能力；CRM 和电商均强制依赖用户管理，沿用自动安装、联动启用与停用保护规则。所有电商站点统一要求买家登录后才能下单；该边界不预设底层认证代码能否复用或账号是否共表，见 [ADR-0006](adr/0006-required-admin-optional-visitor-accounts.md) 与 [ADR-0007](adr/0007-required-plugin-dependencies.md)。

首个管理员通过受保护的初始化页面建立，使用部署时提供的一次性初始化凭据，选择并验证登录身份后创建；成功后凭据失效且入口不再创建管理员。后续成员由具备成员管理权限的人邀请并分配权限，受邀者验证身份后加入。后台支持按配置开放的 Google、微信网站扫码和邮箱一次性登录链接；渠道验证成功后仍检查成员资格与权限，前台自动注册不授予后台成员身份。初始化凭据交付与失败处理、渠道配置契约及邀请生命周期待设计，见 [站点业务后台](business-admin.md)。

后台角色与授权已确认采用必需 RBAC 基础插件，见 [RBAC 设计](rbac.md) 和 [ADR-0009](adr/0009-required-rbac-provider.md)。核心保留统一服务端授权入口，RBAC 提供角色策略；随后台自动安装并联动启用，依赖期间拒绝停用，授权缺失或故障时不放行受保护操作。支持预设模板与自定义角色，管理员可以创建角色并选择权限；一个成员可以分配多个角色，操作权限取并集，仍受站点、资源和业务状态约束。具体模板、权限矩阵、授权管理边界、接口与故障恢复步骤仍待细化。

普通角色的创建、修改和删除已确认可以由具备角色管理权限的非 `owner` 后台成员控制。权限配置在角色上，成员只通过分配角色获得权限，角色管理权限本身同样经角色授予；不增加成员单项权限或个人可授予权限清单。具体角色管理保护规则和成员角色分配的操作权限已在 v1 提案中给出，尚待整体评审，此授权不包含 `owner` 系统角色管理。

已确认保留受保护的站点所有者 `owner` 系统角色，首个管理员自动获得，禁止移除最后一位有效所有者。支持多个 `owner`，现有有效所有者可向本站其他后台成员授予该角色；追加授予后原所有者仍保留角色。`owner` 自动拥有本站全部已注册后台权限及新增插件权限，仍受成员状态、插件启用、站点与资源边界和业务状态校验约束；所有者撤销和转移规则仍待确认。

操作人及其 agent 任务仅编辑插件、主题和组装配置。核心系统通过独立仓库与核心维护流程演进，不按站点需求直接修改或分叉。页面和视觉需求落在主题，业务需求落在插件；详细边界见 [主题与操作边界](themes.md)，仓库职责见 [仓库结构](repositories.md)。

Cloudflare 平台 API 与站点开放 API 是两类接口：前者用于托管基础设施操作，后者由交付程序提供，用于站点维护。具体哪些动作归属哪类接口，需要在维护流程中逐项设计，不能假定站点开放 API 能直接替代构建、部署或基础设施配置。

同一套源码支持两个运行目标是已确认要求；首版完整数据导出并恢复到 Cloudflare 或 Node.js 也已确认。托管资源位于客户自有 Cloudflare 账户，由团队授权代管，见 [ADR-0010](adr/0010-customer-owned-hosting-and-portable-data.md)。数据库、文件存储、定时任务和插件依赖的适配仍需设计和验证，不能将需求确认写成迁移已经实现。

建议让托管与用户自部署共用站点版本记录，外部调用方使用有文档、可版本化的站点开放 API。版本记录和 API 契约的具体形式尚未确认。已确认的交付边界见 [ADR-0001](adr/0001-source-first-delivery.md)。

## 3. 将“可维护”转化为可验收目标（建议）

- 接手者能在明确版本的环境里安装、启动和构建站点，知道核心、插件和项目定制代码分别在哪里。
- 依赖与插件版本可追溯；能判断升级是否兼容，以及需要迁移哪些配置和数据。
- 对仍由内部管理端维护的项目，后续生成和升级应保留其已有项目定制，具体机制待设计；客户自行修改后的源码版本回流不在要求范围。
- 发布失败时能识别失败版本并恢复服务；代码回退与数据恢复分别说明，不能假设恢复旧代码就能回退数据库。
- 站点的内容、文件、插件数据、配置和外部服务依赖有清单；密钥单独交接。
- 源码交付应能由用户在两种目标环境运行；已确认完整数据导出并恢复到两个目标，具体范围和恢复验收见 [交付基线提案](site-deliverable.md#8-客户账户托管与完整数据交付)。

除已单独确认的要求外，以上细化建议尚未整体成为验收承诺；具体操作步骤和可量化标准继续按交付基线收敛。

## 4. 插件生命周期：已确认边界与待设计规则

已确认插件在构建阶段安装，运行时控制已安装插件的启用状态。新增、升级及从交付产物中移除插件通过构建与发布完成；运行时开关不改变插件代码版本。此决策见 [ADR-0002](adr/0002-build-time-plugins-runtime-enablement.md)，状态、依赖和验收建议见 [插件生命周期](plugins.md)。

安装所选插件时，构建流程按依赖声明递归补齐必需插件。CRM 强制依赖用户管理，操作人只选择 CRM 也会安装用户管理。运行时启用 CRM 时自动联动启用已安装的用户管理，检查配置和依赖就绪状态；依赖未就绪不能将 CRM 标记为已启用。安装与启用分别执行，运行时不安装代码，见 [ADR-0007](adr/0007-required-plugin-dependencies.md)。

停用仍被已启用插件必需依赖的能力时，拒绝操作并列出依赖者；CRM 启用期间不能停用用户管理，需先停用 CRM 及其他仍依赖用户管理的已启用插件。不自动联动停用依赖者；依赖检查通过后，仍需满足插件自身在途业务等停用条件。

| 阶段 | 需要作出的产品选择 |
| --- | --- |
| 选择与安装 | 已确认构建时自动补齐必需依赖，安全性由注册操作人评估；插件来源、注册方式与版本管理待设计 |
| 组合 | 已确认 CRM 和电商强制依赖用户管理；依赖声明格式、可选能力和冲突如何处理，两个插件争用同一路由时怎么办？ |
| 启用 | 已确认自动联动启用已安装的必需依赖，检查配置与就绪状态；失败恢复、生效时限和多实例一致性待设计 |
| 运行 | 插件可以访问哪些数据、密钥和外部服务；失败后影响一个功能还是整个站点？ |
| 升级 | 新版本通过重新构建发布交付；核心和插件兼容性、迁移与恢复策略待设计 |
| 停用 | 已确认有启用中的依赖者时拒绝停用并列出依赖者；页面、后台菜单、任务、API 及在途业务的处理继续设计 |
| 卸载 | 默认保留还是删除数据；再次安装能否恢复？ |
| 替换 | 相同功能的不同插件能否互换；数据转换由谁提供？ |

已确认按可信插件模型设计：注册插件的操作人负责安全性评估，系统不提供插件安全审查或恶意代码沙箱隔离。依赖校验、配置校验、生命周期与故障恢复仍属于插件运行契约；业务模块的账号权限和交易校验按其自身规则实现。见 [ADR-0003](adr/0003-operator-trusted-plugins.md)。

## 5. 首版业务范围与验收场景

已确认首版提供企业展示模块、外部客服接入模块、电商模块组和标准用户管理；CRM 作为可选增强插件提供完整客户运营能力，为销售管理保留扩展接口。这里的“模块”表示业务功能范围；一个模块对应一个还是多个插件，尚未决定。提供这些能力与每个生成站点是否启用这些能力，是不同的范围。

| 模块 | 已确认 | 仍需澄清 |
| --- | --- | --- |
| 企业展示 | 首版必须包含 | 页面与内容范围；是否包含产品、服务、案例；内容由谁通过什么方式维护 |
| 客服 | 接入外部客服服务 | 服务商、访客入口、身份与订单上下文对接、数据归属及配置维护 |
| 电商 | 单商家 B2C 实物零售；市场灵活配置；同站点多交易币种，各 SKU 按币种独立定价、可仅配置部分币种售价，缺价币种不可购；一单一种交易币种；购物车切币重报价，缺价商品保留并阻止结算；登录时自动合并购物车，沿用登录前当前币种，同 SKU 数量相加并校验价格库存；匿名购物车在当前浏览器保存，账号购物车服务端保存并可跨设备继续使用；默认匿名 30 天/账号 90 天、按最后修改计时且可配置；国内与国际支付；主流物流接入，聚合平台优先；业务能力可拆分；强制依赖用户管理，未登录可浏览与加购，提交订单前必须登录 | 购物车同步冲突及期限配置变更的生效规则、市场/结算规则、具体支付与物流适配器、完整交易闭环与验收细节 |
| 用户管理 | 首版提供可选的访客用户管理插件，支持按配置生效的 Google、微信网站扫码登录及邮箱一次性登录链接，首次验证成功自动注册并登录；安装 CRM 或电商时自动带入；每站必备后台成员登录与授权，后台渠道见 R50 | 微信接入配置、邮件服务与链接生命周期，两类账号的生命周期、权限及关联，后台登录配置契约 |
| CRM | 可选增强插件，强制依赖并自动安装用户管理；首版完整客户运营；为后续销售管理保留扩展接口 | 客户运营具体流程、营销范围、与电商和客服的关联，以及扩展契约 |

电商的候选模块、交易一致性要求和验收场景单独维护在 [电商需求基线](commerce.md)。电商能力通过插件扩展；最小运行时核心不因新增电商而默认内置订单、库存或支付业务模型。

商家所在地、销售目的地等按站点配置，具体服务范围由所启用的业务规则及供应商能力共同决定。主流物流接口以统一业务契约和物流适配插件承接，候选设计与官方参考见 [市场与物流](shipping.md)。

用户管理与 CRM 的建议职责、数据归属、插件依赖和验收场景维护在 [用户管理与 CRM](users-crm.md)。CRM 增强基础用户模块，不应成为登录、下单或支付的强制依赖；这属于待确认的设计建议。

此前提出的博客、联系表单只是访谈示例，尚未纳入首版需求。

以下是基于已确认模块的候选验收场景；具体操作步骤待模块细化后补齐。

1. 生成包含企业展示和客服入口的站点，交付源码；另一位开发者接手并修改展示页面。
2. 相同需求选择托管交付，维护者更新企业展示内容；插件升级后保留这些修改。
3. 为已有站点增加一个功能，检查是否只需添加插件和配置，是否需要改核心。
4. 停用客服相关插件后，企业展示仍按约定运行，客服入口有明确处理；若插件存储数据，需验证其保留和导出规则。
5. 一个插件依赖另一个插件时，阻止不兼容的卸载或提供明确的替代处理。
6. 插件升级涉及数据库变更，演示失败后的恢复过程并说明是否会丢失新数据。
7. 同一份交付源码分别在 Cloudflare 和标准 Node.js 部署，并验证所选业务功能及站点开放 API。
8. 完整数据导出及恢复到 Cloudflare 或 Node.js 已确认为首版要求；具体验收包含目标新存储、关系与文件校验、身份和在途业务处理，见交付物 DL10–DL17 提案。
9. 按选定交易模式验证商品管理、购物、下单、支付、履约、售后及运营管理闭环，包含并发、重复回调和故障恢复；详见电商需求基线。
10. 用户管理独立运行；可选安装或停用 CRM，并验证用户、订单、客服和 CRM 数据的访问权限与关联规则。
11. 构建时安装插件后，在不重新构建的情况下控制其启用状态，验证服务端入口、页面、后台入口和任务按规则生效；未安装的插件不能通过运行时开关启用。
12. 管理端不可用时仍可登录交付站点的业务后台，管理已启用插件的业务；新增插件注册其管理功能，无需向通用后台核心添加专属业务分支。
13. 生成任务产出可预览版本后等待操作人选择继续修改、交付源码或正式发布；选择与相应源码、构建结果和版本关联。
14. 按需求组装、生成或编辑插件及主题后，可构建站点及对应业务后台；核心源码无改动，缺少扩展契约时报告能力缺口。
15. 不安装访客用户管理插件，生成企业展示和客服站点；后台成员仍能登录并管理内容及客服配置，站点不提供访客注册或登录。
16. 仅选择 CRM 后构建，用户管理作为必需依赖自动纳入交付物，安装清单可追溯该依赖关系；不要求操作人先单独安装用户管理。
17. CRM 与用户管理已安装但未启用时，只启用 CRM 即自动启用用户管理；依赖配置或启用失败时，明确报告原因且不能将 CRM 标记为已启用。
18. CRM 已启用时请求停用用户管理，操作被拒绝并列出 CRM，两个插件保持原启用状态；先停用所有已启用的依赖者后，才可按用户管理自身规则请求停用。
19. 仅选择电商时，构建自动带入用户管理，启用电商时联动启用用户管理；CRM 或电商任一依赖者仍启用时均拒绝停用用户管理。
20. 未登录或登录已失效的买家提交订单时，页面提示登录，服务端拒绝创建新订单；登录后以当前登录身份下单，不能通过提交其他账号 ID 改变购买主体。
21. 未登录时可以浏览商品并加入购物车，进入提交订单流程时要求登录；浏览与加购不被提前拦截，也不因登录前加购而允许匿名创建订单。
22. 登录已有前台账号，完成新登录身份验证并主动绑定；使用已绑定的其他方式重新登录后，仍访问同一账号及其订单，不因切换登录渠道创建新账号或转移订单。
23. 绑定的目标身份已属于另一前台账号时，拒绝绑定并提示使用原账号；即使用户能验证两个账号，首版也不提供合并，身份、资料和订单关联保持不变。

| Q64 | 用户登录时，匿名购物车与账号已有购物车如何衔接？ | 已确认：A，自动合并，相同 SKU 数量相加，重新校验价格和库存；合并币种见 Q65，保存及跨设备范围见 Q66，保存期限见 Q67，同 SKU 数量冲突见 Q68 |
| Q65 | 登录合并时，两份购物车币种不同，采用哪一种？ | 已确认：A，沿用登录前当前匿名购物车币种，统一按该币种独立售价重新报价；缺价商品沿用 R70 保留并阻止结算，不换算旧报价 |
| Q66 | 首版购物车的保存和跨设备使用范围？ | 已确认：A，匿名购物车保存在当前浏览器，账号购物车由服务端保存，可在其他设备登录同一账号后继续使用；保存期限见 Q67，同 SKU 数量冲突见 Q68 |
| Q67 | 匿名和账号购物车保存多久？ | 已确认：A，默认匿名 30 天、账号 90 天，均从最后一次购物车修改起计时，允许按站点配置；过期清理只影响购物车，不影响历史订单 |
| Q68 | 多设备同时修改同一购物车商品数量，如何处理基于旧内容提交的冲突修改？ | 已确认：A，拒绝基于旧内容的冲突修改，提示刷新后重新确认；随电商延期，不继续追问该模块细节 |

### 8.1 已确认 Demo 范围

使用“企业展示站＋公告插件＋独立业务后台”贯通系统：先有固定核心与基础展示能力，再由真实 agent 按需求新生成公告插件及其后台管理、修改主题，经过构建验证给出预览；操作人再提出一次修改，得到新版本，最后交出可独立运行的源码。

| 层次 | 本期验证 | 后置 |
| --- | --- | --- |
| 内部管理端 | 一个内部操作人、一个演示项目、串行执行任务；需求输入、插件选择、任务日志、变更、构建结果与预览 | 多人协作、复杂并发调度、计费、集中跨站点业务运营 |
| 生成能力 | 复用已有展示能力，真实生成一个新业务插件和后台扩展；修改主题并至少完成一次后续修改；站点生成期间核心不变 | 插件市场、通用任意业务生成保证、自动核心升级 |
| 交付站点 | 展示页、公告的公开读取和后台增改删；独立后台；最小真实登录及纯角色授权，证明允许读取与拒绝越权修改 | CRM、访客账号体系、外部客服；全部登录渠道、完整授权管理和所有者转移界面 |
| 插件机制 | 构建安装与声明依赖补齐、后台注册、运行时启停及依赖停用保护；停用时页面、API 与后台行为一致 | 电商、支付、库存和物流；复杂在途业务补偿 |
| 运行与数据 | 同一份站点源码分别在 Node.js 与 Cloudflare 运行目标验证；对 demo 实际持有的数据和文件完成最小完整导出/恢复闭环 | 全量产品业务状态迁移、历史版本自动升级、零停机迁移、备份服务等级 |
| 源码交接 | 固定版本源码、依赖与运行说明；关闭管理端及 agent 后站点仍可独立运行 | 客户账户批量接入、自动域名管理、生产托管控制台和运维自动化 |
