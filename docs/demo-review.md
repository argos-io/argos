审查日期：2026-11-08。进度更新：2026-11-09。状态：首轮静态审查、Q73–Q75 需求澄清及技术契约补充完成，T0–T5 已修订、待执行确认；未开始功能实现、安装依赖、调用模型或部署。审查基线为提交 `9b1caa1` 的 [需求](requirements.md)、[技术方案](demo-design.md)、[任务](demo-tasks.md)及相关 ADR。

本轮发现的需求歧义已作出决定，技术契约及验证门槛已补入设计，具备从 T0 开始受控编码验证的条件。Astro＋React＋Hono 的实际集成、D1 和真实执行器尚待验证，不能将本审查当作系统可行性已证明。以下保留发现、处理与验收状态，不将电商、完整 RBAC v1 和生产运维重新列为 demo 前提。

P1 表示在相应模块实施前必须解决的契约缺口；P2 表示必须补入实施验证的约束。严重度不表示已经发现运行中的漏洞，当前尚无运行代码。本文建议未经用户确认不自动变为产品要求，官方能力核对也不等于集成已经通过。

## 1. 需求与契约缺口

### DR1 · P1：预览数据归属（需求已澄清）

审查发现：原[技术方案第 5 节](demo-design.md#5-工作台流程与版本)仅固定输入源码、构建及预览记录，[DM2](requirements.md#82-已确认-demo-完成标准)仅要求原版可定位，没有规定数据是否共用、继承或重置。

已确认：用户同意第一期采用简化方案，预览共用测试数据，续改保留已录入的公告、内容和文件；旧版本保留源码与构建记录，不为每个版本复制数据库和文件。继续使用同一数据环境的预览会看到相同数据变更，本期不要求多个历史预览独立操作。

边界：同一项目、同一运行目标内共用数据；双目标各自的资源通过已约定的导出/恢复验证。自动验证不能写共享预览数据，接入新旧源码前检查数据模式兼容。历史源码记录与导出切点的数据包分别管理；Q74 已确认本期遇到需要转换旧数据的续改先暂停说明。

处理：**Q73 的需求歧义已关闭，实施验收待验证**。已同步 R80、DM2/DM6、技术方案和 T4/T5，确认不等于数据保留用例已经通过。

### DR2 · P1：续改的数据兼容边界（需求已澄清）

审查发现：原[最小插件契约](demo-design.md#3-最小插件契约)仅规定版本化 JSON，允许继续修改插件，而恢复要求模式不匹配时失败，缺少对续改的明确边界。

影响：例如 agent 将公告图片字段改名、必填字段增加或记录类型替换，旧数据仍是旧模式。源码构建可以通过，而旧内容读取失败、文件引用丢失或数据包无法恢复。模式版本号本身不能完成转换，也不能证明修改兼容。

已确认：Q74 采用 A，首期保证旧内容可用，需要转换已有数据时暂停并说明；用户追加后期提供标准方案，按上下文记为标准数据迁移目标。新插件首次声明模式、空存储初始化和经验证的兼容修改仍属本期范围。后期的核心编排、插件转换和恢复流程草案统一见[标准迁移方案](plugins.md#41-后续标准数据迁移方案草案)。

处理：**Q74 的需求歧义已关闭，兼容检查及暂停路径待实施验收**。记录类型、模式、记录/文件引用声明纳入本期契约；未知模式、缺失引用或有数据的插件被直接移除均须明确拒绝，不能靠重置数据通过验收。

### DR3 · P1：授权与业务写入的共同原子契约（方案已补充）

审查发现：原[技术方案第 4 节](demo-design.md#4-身份数据与原子操作)同时要求固定 SQL 批次、禁止任意交互式事务、提交时重新检查授权和修订，但未定义执行协议；完整 [RBAC v1](rbac.md#71-v1-建议统一提交与初始化)另有更强的工作单元提案，尚未整体接受。

影响：实现者若先在 JavaScript 检查角色，再执行记录更新，撤权或停用可插入两步之间。若多语句批次中的前置条件只更新零行、后续语句仍写入，也可能留下部分业务结果；返回之后才检查行数不能撤回已提交批次。当前文档已经提醒零行更新问题，但没有定义可复用的执行协议。

处理方案：技术方案已列出初始化、邮件凭据确认、内容/文件关联写入及插件状态命令，采用核心生成的每次全新执行标记、全部写入受本次标记控制及批次内后置断言；稳定幂等键与执行标记分别管理。RBAC 提供同边界复核条件，业务插件不获得任意 SQL/平台事务。后置断言在批次内失败并触发回滚，不在提交之后补判定。完整协议统一维护在技术方案。

验证状态：**Node.js 内存原语验证 9 项通过；真实适配、D1 对照与并发门槛待 T0**。未证明前不冻结存储公共接口，也不将本地原语等同于完整 RBAC 或命令执行器。

### DR4 · P1：主题与业务插件的页面归属（方案已补充）

审查发现：[主题职责](themes.md#职责划分)与原静态注册同时描述页面入口，原 T4 又要求新公告插件提供 Astro 页面，但未规定覆盖、冲突、保留路径及业务归属。

影响：两个插件或主题都声明 `/news` 时，构建注册顺序可能决定实际行为；主题的首页读取公告但路由只属于主题时，也不能简单地只检查主题开关。新增插件可能必须临时修改核心路由分支才能展示，违背生成边界。Hono 与 Astro 的检查入口若分别实现，还可能有直接 API 或页面遗漏状态检查。Astro 官方还明确提示原始请求路径未必等于最终匹配路径，因此在分发前仅按 URL 字符串前缀授权会有绕过风险。

处理方案：已补充[唯一页面组合契约](demo-design.md#31-页面组合与唯一归属)，由业务逻辑页面、主题呈现及显式组装映射生成唯一静态入口。覆盖、冲突、必需/可选业务来源及核心保留路径有明确处理；检查绑定匹配路由与业务查询，不能只匹配 URL 前缀。

验证状态：**设计已补充，T0 验证最小组合，T1/T3 验证冲突、状态及路径绕过**。不建设通用多框架或多主题切换引擎。

### DR5 · P1：文件入口及提交一致性（方案已补充）

审查发现：公告规则只允许公开已发布内容，但原文件适配仅定义逻辑 ID 和目录/R2，未规定访问、暂存、关联及冻结的共同协议。

影响：若图片通过静态目录或公开 R2 URL 返回，知道地址后仍能访问草稿、撤下或停用插件的图片；数据库与文件分两次写入，失败时还可能留下不存在的引用。维护模式若只挡后台保存，却未挡上传或清理，也无法得到一致数据包。

处理方案：已补充[文件访问与提交契约](demo-design.md#32-文件访问与提交)，约定私有存储、按有效引用检查、暂存后关联、孤立对象处理以及维护冻结。已提交媒体即使暂时无引用或插件停用也纳入完整导出，暂存对象单列，恢复验证实际文件。

验证状态：**设计与 T1/T3/T5 已同步，文件访问和数据库/文件故障用例待实施**。

### DR6 · P1：工作台访问与预览隔离（方案已补充）

审查发现：原管理端边界仅以单人、本机监听为部署前提，要求预览独立来源，但未规定管理 API 身份、来源检查和 cookie 范围。

影响：把工作台和预览仅分到同一主机名的不同端口，并不能隔离 Cookie。预览或其他浏览器页面仍可尝试向本机服务发送请求；CORS 不等于对执行任务、导出和文件操作的授权。

处理方案：技术方案第 4–5 节已约定独立工作台访问凭据、Host/来源/CSRF 检查、预览不同主机名及独立 cookie，凭据不交给预览或执行器；执行进程必须真实停止后才能继续同项目写任务，无需扩展成团队账号系统。

验证状态：**设计与 T4 已同步，拒绝用例和进程退出验证待实施**。

### DR7 · P1：邀请与登录的身份验证（需求已澄清）

审查发现：原方案先实现 Google 登录，但邀请的身份匹配、有效期及消费流程未定义；把邀请邮箱也限制为 Google 托管邮箱会额外收窄需求。

已确认：Q75 采用普通邮件邀请及一次性链接确认，完成邮箱验证后加入后台；日常登录也使用邮件链接，无 Google 账号要求。本期真实认证验收改为邮箱，Google 与微信的后续按配置接入要求保留。邮箱登录身份、内部稳定成员 ID 及角色分别维护，不以邮箱相同自动关联第三方身份。

技术边界：链接绑定站点、邮箱、用途、失效时间和单次消费事实。GET 仅打开确认页，明确确认后通过受来源和 CSRF 保护的请求原子消费、授予既定角色并建立会话。普通登录只面向已有有效成员，不能用登录链接创建后台资格；初始化仍同时验证一次性初始化凭据。过期、重放、用途混用、邮件发送失败及恢复后的旧凭据均有拒绝路径，详见[认证方案](demo-design.md#4-身份数据与原子操作)。

处理：**Q75 的需求歧义已关闭，真实邮件验证待实施验收**。邮件传输是本期必要外部条件；完整邀请管理界面、邮箱变更和账号恢复产品后置。原 Google 测试应用不再是本期必需前提。

## 2. 实施验证缺口

### DR8 · P2：关键可行性验证顺序（计划已修订）

审查发现：原任务顺序先建立 Node.js 契约和真实后台，再接 Workers，最后才真实执行 SDK；未验证容器内执行或两套平台实际构建。

影响：Node.js 的接口和页面完成之后，才可能发现 Worker 打包泄漏 Node API、请求链不兼容、只读依赖妨碍构建缓存写入，或容器里的 SDK 认证/沙箱/网络无法运行。仅把重启后的任务标为中断，也不能保证旧执行进程已经停止写入。

处理方案：任务已增加 T0，先做最小双目标组合及原子命令门槛，再开始正式站点实现；具备条件时尽早做真实容器执行器，早于完整工作台。外部小项未验证时明确留空，本地门槛通过后仍可推进不依赖该条件的开发。

Cloudflare adapter 的默认图片处理可能自动增加 Images binding，不能无意扩大本期 D1/R2 资源范围；按本期无需变换的图片契约显式配置并检查最终资源清单。外部条件不足时保留“未验证”，不通过替换版本、降低权限检查或模拟事件消除失败。

验证状态：**T0–T5 已修订，Node.js 原语实验不代替 T0 的集成门槛**。尚未构建或部署应用，也未调用模型，不改变已接受的框架方向。

## 4. 核对依据

- [Astro Hono routing API](https://docs.astro.build/en/reference/modules/astro-hono/)与[路由集成说明](https://docs.astro.build/en/guides/routing/#using-with-hono)：提供请求处理器及组合方式，不提供 Argos 的页面归属、依赖与授权规则。
- [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)：批次由预先提供的语句组成，语句失败可回滚；零行条件写入的业务冲突仍需应用契约处理。
- [Cloudflare R2 公共存储桶](https://developers.cloudflare.com/r2/buckets/public-buckets/)：公开访问直接暴露对象，不能用站点页面开关替代对象访问控制。
- [RFC 6265 第 8.5 节](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)：Cookie 不按端口隔离；主机与凭据边界必须明确。
- [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect)：Google 稳定用户标识为 `sub`，邮箱可能变化，邀请匹配和账号标识不能混为一谈。
- [OpenAI Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)及[执行安全说明](https://learn.chatgpt.com/docs/agent-approvals-security)：SDK 支持服务端线程；容器可能限制内层沙箱，目标执行环境必须实际验证。
- [Astro Cloudflare adapter](https://docs.astro.build/en/guides/integrations-guide/cloudflare/#imageservice)：默认图片服务涉及 Cloudflare Images binding，需要显式约束本期资源。

以上均为本轮只读查阅的官方资料。文档核对支持能力和限制判断，不替代编译、并发用例、真实登录、模型任务和云端恢复验收。
