# 电商模块组：需求基线与待确认范围

状态：讨论稿。更新：2026-11-08。本文细化 [系统需求](requirements.md) 中的电商范围；未作技术选型，未实施交易或支付集成。

分期更新：电商已移出第一期可行性 demo，本文需求和候选设计保留为后续参考，暂不继续逐项澄清，也不作为 demo 开工条件。此前“首版”均指原电商产品目标，当前优先级以 [ADR-0012](adr/0012-feasibility-demo-first.md) 为准。

## 1. 已确认要求与交易基线

已确认：首版需要专业的标准电商能力，包括完整商品管理、支付等功能；允许拆为多个模块，按站点需要组装。

已确认首版以单商家、B2C、实物商品零售为基线，覆盖商品、库存、购物、下单、支付、配送履约及售后的完整流程。“单商家”针对每个交付站点，管理端仍可以维护多个不同商家的站点。

已确认电商强制依赖用户管理：构建时自动安装用户管理，启用电商时自动联动启用已安装的用户管理并检查配置与就绪状态；电商仍启用时拒绝停用用户管理，列出电商等已启用的依赖者，见 [ADR-0007](adr/0007-required-plugin-dependencies.md)。

已确认所有电商站点统一要求买家登录后才能下单，不提供访客购买或按站点开放未登录购买的配置。未登录或登录失效时，服务端拒绝买家创建新订单，页面引导登录；购买主体由服务端登录身份确定，不能以客户端提交的账号 ID 或联系方式代替登录。该要求针对买家下单，支付回调与已创建交易的后续处理按各自认证和业务规则执行，不依赖买家保持在线登录。

已确认登录拦截位于提交订单前：未登录可浏览商品和加入购物车，无需在浏览或加购时先登录。用户登录时自动合并匿名购物车与当前账号已有购物车，相同 SKU 数量相加，重新校验价格和库存，不先提示选择购物车。两份购物车币种不同时，沿用登录前当前匿名购物车币种，全部商品按该币种独立售价重新报价；缺价商品保留并阻止结算，不将旧报价按汇率换算。匿名购物车保存在当前浏览器，账号购物车由服务端保存，其他设备登录同一账号后可继续使用；默认匿名保存 30 天、账号保存 90 天，均从最后修改起计时，允许按站点配置；仅浏览或刷新不续期，过期清理不影响历史订单。同 SKU 数量冲突按 Q68 拒绝基于旧内容的修改，其他并发细节及期限配置变更的生效规则后续设计。匿名加购不自动形成订单或授予账号数据访问权，购物车合并不属于账号合并，也不转移其他账号的数据。

商家所在地与销售目的地需要灵活配置，不固定为某一组市场；物流要求支持业界主流接口协议接入，首版聚合平台优先，并保留承运商直连扩展接口。具体市场配置、物流契约与适配建议见 [市场与物流](shipping.md)。

已确认首版同一电商站点支持多种交易币种，不限定每站一种币种；每个 SKU 按币种独立维护售价，并以不同交易币种下单和付款，不采用自动汇率定价或自动换算加独立价格覆盖。允许仅配置部分启用币种的售价，缺价币种不可购，不要求配齐全部币种才能上架。单笔订单固定使用一种交易币种，商品、优惠、运费、税费及总额均使用该币种，不支持一单混合币种。购物车切币时按目标币种独立售价重新报价，缺价商品保留并标记不可购，用户移除缺价商品或切回可购币种后才能结算。展示换算、退款及服务商结算规则仍需细化。该决定不表示所有市场、币种和支付渠道组合均已可用，见 [ADR-0011](adr/0011-multi-currency-commerce.md)。

首版支付已确认同时覆盖国内和国际渠道，由可选支付插件承接，按站点需要在构建中安装并在运行时配置启用。微信支付、支付宝、Stripe、PayPal 是讨论中给出的候选示例，尚未确定具体首批适配器名单，也不表示每个站点必须安装或启用所有渠道。

数字商品、订阅、B2B 采购和多商家平台不作为本次首版交易基线，其扩展方式留待后续需求确定。本章已明确交易模式；以下各模块的具体功能、渠道与验收细节仍需澄清，不能将候选完整清单直接视为全部已经确认。

## 2. “对齐业界”的可检查依据

区分领域实践、供应商接口契约和特定市场要求，避免把某个框架当作统一行业标准。

| 对齐对象 | 已核实事实 | 本项目的使用方式 |
| --- | --- | --- |
| [Medusa Commerce Modules](https://docs.medusajs.com/resources/commerce-modules) | 分别提供商品、价格、购物车、订单、支付、库存、履约、促销和税费等领域能力 | 用于检查领域覆盖和模块边界，不直接决定采用 Medusa |
| [Medusa 商品](https://docs.medusajs.com/resources/commerce-modules/product) 与 [库存](https://docs.medusajs.com/resources/commerce-modules/inventory) | 商品管理和库存分别建模；库存包含预留与可用性管理 | 用于审查商品、变体与库存的职责，具体模型由本项目设计 |
| [Vendure 订单模型](https://docs.vendure.io/current/framework/core-concepts/orders) | 用状态机管理订单推进，区分支付授权、结算和部分履约等状态 | 用于设计合法业务转换与部分处理场景，不照搬其状态名称或实体划分 |
| [Stripe 履约指南](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page) | 自动履约需要依赖服务端事件；用户不一定返回支付完成页 | 支付完成不能仅根据浏览器跳转判断 |
| [Stripe Webhooks](https://docs.stripe.com/webhooks) 与 [幂等请求](https://docs.stripe.com/api/idempotent_requests) | 事件可能重复、重试或乱序；API 提供幂等请求机制 | 作为支付可靠性设计与故障验收的参考；实际协议跟随选定支付渠道 |

以上来源于 2026-11-06 的官方文档调研，不是对本项目的功能实现、部署兼容或认证结论。Stripe 仅为参考，尚未选定服务商；市场可配置，税费、发票及渠道能力需按目标站点具体配置和验证。

## 3. 候选模块与职责

业务模块不等于独立服务或独立进程。优先建立清晰的数据与操作边界，再决定插件包粒度，避免拆分后每个模块都难以维护。

| 候选模块 | 建议覆盖的能力 | 关键边界 |
| --- | --- | --- |
| 商品目录 | 商品创建、编辑、发布与下架；分类、集合、属性、规格、变体、SKU、图片、详情、搜索筛选；批量导入导出及校验 | 商品发布状态与库存可售状态分开；历史订单保留成交时商品快照 |
| 定价与促销 | 已确认同站点多交易币种且每个 SKU 按币种独立定价，可仅配置部分币种售价，缺价币种不可购；一单一种币种；价格、币种、有效期；折扣、优惠码、适用条件、叠加与分摊规则 | 服务端计算；金额精度、舍入及促销复杂度待确认 |
| 库存 | 库存数量、可用量、预留、释放、扣减、调整与变动记录 | 明确预留时机与超时；并发下防止超卖；多仓支持范围待确认 |
| 购物车与结算 | 未登录可加购；增删改商品、数量校验、地址、配送和支付方式选择；价格、优惠、税费、运费汇总；已确认切币按独立售价重报价，缺价商品保留并标记不可购；登录时自动合并，沿用登录前当前币种，同 SKU 数量相加并校验价格库存；匿名浏览器保存，账号服务端保存并可跨设备继续使用 | 提交订单前必须登录；缺价商品未移除或未切回可购币种时不能结算；默认匿名 30 天/账号 90 天、按最后修改计时且可配置；同 SKU 数量冲突按 Q68 拒绝旧内容修改；其他并发细节及期限配置变更的生效规则后续设计，提交时重新验证可售性和报价，说明价格变化如何让用户确认 |
| 订单与交易编排 | 创建订单、成交快照、订单查询、取消、超时关闭；协调支付、库存和履约 | 不把订单、支付、履约状态压成一个字段；跨模块失败与重试有持久记录 |
| 支付 | 国内与国际渠道接入；支付会话、支付尝试、状态查询、授权与扣款能力声明、全额和部分退款、失败原因、渠道交易映射 | 统一领域契约与可选 provider 插件；具体首批名单、适用市场、币种和能力矩阵待确定 |
| 配送与履约 | 可配置配送区域、运费规则、发货、面单、运单和物流状态、部分发货、取消履约 | 已要求主流物流协议接入；首批 provider、能力矩阵和自动对接范围见物流文档 |
| 售后 | 退款申请与处理记录；退货、验收、补库存；按订单行和数量处理 | 退款、退货与库存回补是不同动作，明确是否联动；换货范围待确认 |
| 客户 | 交易客户资料、登录账号关联、收货与账单地址、订单访问 | 下单必须登录；登录和账号生命周期复用用户管理；交易客户与账号明确关联；历史订单保留成交时快照；CRM 为可选增强 |
| 税费与单据 | 含税或未税定价、税额与明细、单据记录及税务服务接口 | 根据可配置市场定义支持规则；收据、商业单据和法定发票分别定义 |
| 运营后台、API 与通知 | 商品、订单、支付、退款和库存操作界面；角色权限、审计、基础报表、数据导出、订单与支付记录核对、交易通知及失败重试 | 后台与 API 使用同一业务规则；业务通知与核心交易结果解耦 |

本表为候选完整范围，不表示全部以独立插件交付，也不预先承诺多仓、多币种结算或所有营销、税务、物流场景。

## 4. 对运行时与插件契约的影响（建议）

已确认所有插件必须在构建时安装，运行时可控制启用状态；以下交易与生命周期规则为在此边界下的设计建议，详见 [插件生命周期](plugins.md)。

- 最小运行时提供通用扩展能力；商品、订单、支付等模型属于可选电商模块组，不放进所有站点必装的核心。
- 电商领域契约与支付、配送、客服等供应商适配分开；替换供应商不要求重写商品与订单模块。
- 访客用户管理按站点功能需要安装，后台成员登录与授权是每站必备基础能力；CRM 和电商均强制依赖用户管理，沿用自动安装、联动启用与停用保护规则。所有电商站点的买家下单必须登录；登录和账号生命周期复用用户管理契约，交易客户和订单仍由电商维护。CRM 可订阅获授权的业务事件提供客户视图，交易正确性不依赖 CRM 可用。具体身份映射见 [用户管理与 CRM](users-crm.md)。
- 已确认一个前台账号可主动绑定多种登录身份；买家换用已绑定的 Google、微信或邮箱登录时，继续访问同一账号及其订单，订单不因登录渠道变化而转移。
- 首版不提供账号合并；目标身份已属于另一账号时拒绝绑定，两边订单、交易客户与账号关联保持不变，CRM 联系人合并不能代替账号合并或转移订单关联。
- 跨模块操作通过明确的命令和契约完成，不直接修改其他模块的表；依赖、事件和版本约束有清单。
- 订单、支付、退款、履约及库存各自保留业务状态与可追溯记录；不把外部渠道状态直接当作内部完整状态机。
- 对关键交易流程明确事务边界、并发控制、持久任务、重试和补偿；失败后能恢复处理，不能只依靠进程内回调或内存队列。
- 停用插件时区分“停止产生新交易”和“处理存量交易”：在途支付、退款、回调与历史订单仍需按明确策略维护。
- 支付 provider 只有已随构建交付且配置满足要求时，才能在运行时启用；新增或升级 provider 必须重新构建发布。停止接收新支付与保留存量回调、查询和退款处理应分别定义。
- 卸载包含交易数据的插件前，明确依赖检查、数据保留、导出与恢复方式；不得静默删除历史交易。
- 外部客服是否接收客户身份或订单上下文待确认；客服接入本身不授予退款或查询任意订单的权限。
- Cloudflare 和 Node.js 都要验证交易一致性与任务恢复；采用不同平台适配可以接受，具体能力保证必须一致并可测试。
- 若复用现有电商后端，需列明其部署目标、依赖、源码交付与维护方式；不能将仅前端可运行视为完整电商源码交付完成。复用、自建和外部服务方案尚未选定。

## 5. 支付与交易可靠性基线（建议）

已确认国内与国际两类支付覆盖，具体渠道通过适配插件接入。目标市场、交易及结算币种、付款方式与渠道自身支持的能力分别配置和验证；不会因安装某个适配器就推定所有商家账号及市场可用。业务后台注册相应渠道配置、状态查询及交易处理功能。

已确认的同站点多交易币种要求定价、订单快照、支付/退款记录和数据导出明确保留金额与币种，不能通过切换站点默认配置重新解释历史金额。每个 SKU 的各币种售价独立维护，修改一种币种的售价不自动改写其他币种或历史成交价。SKU 可仅配置部分启用币种售价，缺价时服务端拒绝以该币种购买；不因缺少其他币种售价要求整体下架。缺失价格不能当作零元，也不按汇率自动补价。不由前端提交的金额或币种直接决定扣款。

Q62 已确认一单一种交易币种：商品、优惠、运费、税费及总额均使用订单交易币种，服务端不得接受混合币种订单或把不同币种金额直接相加。不同订单可使用不同交易币种；该规则不决定展示换算、退款或支付服务商的结算币种。

Q63 已确认购物车切币规则：有目标币种售价的商品按该币种独立售价重新报价；缺价商品保留并标记不可购，不自动移除、不以零元补价，也不静默跳过后创建订单。用户移除缺价商品或切回可购币种后才可继续结算，其他库存、配送和报价校验仍需通过；服务端执行相同约束，不能只在页面禁用结算按钮。

依据上述官方支付文档和本项目的交付维护目标，建议将以下内容作为实施时的设计与验收要求：

1. 商品单价、折扣、币种及应付总额由服务端计算并记录快照，客户端传入金额不能直接作为扣款依据。
2. 创建订单、发起扣款和申请退款具有业务幂等规则；同一次操作重试不能导致重复订单、扣款或退款。
3. 对支付回调执行渠道要求的真实性校验、对象关联及金额和币种校验，持久记录接收与处理结果，支持安全重放。
4. 处理重复、乱序、延迟与缺失事件；通过状态查询和核对任务修复不一致，不只依赖正常回调路径。
5. 支付成功页只展示状态；浏览器未返回时也能完成服务端交易处理，不能由客户端声明付款成功。
6. 支付渠道超时意味着结果待确认，不能直接认定扣款失败后再次扣款；支付结果明确后再决定释放库存、履约或退款。
7. 部分退款和累计退款有可核验的额度与并发约束；退款结果、退货结果和库存变化分别留痕。
8. 优先通过支付服务商托管收银台或受控组件收集支付凭据；交付程序不直接保存完整卡号或安全码，密钥与业务数据分开维护。
9. 查询订单、修改价格、调整库存和退款分别校验对象访问权与操作权限；记录维护动作，日志中避免泄露支付密钥和完整个人资料。
10. agent 如参与运营，调用受授权的业务 API；由服务端约束金额、状态和权限，不能依靠提示词保证资金操作正确。

具体支付认证、渠道规则和市场义务在渠道与市场确认后设计；此处不作已满足任何认证的承诺。

## 6. 候选验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| EC1 | 建商品、设置两个规格并生成变体、维护价格库存、发布与下架、批量导入含错误数据 | 管理闭环可操作；变体与 SKU 有明确规则；导入错误可定位；下架不改变历史成交记录 |
| EC2 | 未登录浏览、筛选、加购物车，提交订单前登录，再校验报价、下单、支付、实物发货、查看物流和订单 | 单商家 B2C 实物零售全流程闭环可操作，浏览与加购无需登录；登录时自动合并匿名与账号购物车，沿用登录前当前币种重报价，同 SKU 数量相加并校验库存，缺价商品保留并阻止结算，下单关联当前登录身份 |
| EC3 | 两人同时购买最后一件商品 | 按已定义预留与支付策略防止超卖，异常收款有可恢复处理 |
| EC4 | 修改前端金额、折扣或币种后提交 | 服务端拒绝无效请求或重新报价，不按伪造金额收款 |
| EC5 | 重复点击支付；扣款请求超时后重试 | 同一业务操作不重复扣款，能查询最终状态 |
| EC6 | 回调重复、乱序、验签失败；支付成功但浏览器关闭 | 无效事件被拒绝；合法事件不会重复生效或错误回退，服务端可完成处理 |
| EC7 | 支付成功后订单处理或库存操作失败，或任务执行中进程重启 | 持久任务可恢复，失败可定位；按策略完成、补偿或退款 |
| EC8 | 支付延迟成功，但订单已超时且库存已释放 | 按明确策略处理，不直接发货或静默丢弃收款 |
| EC9 | 部分发货、部分退款、重复退款、退货后补库存 | 数量与金额一致；不存在超额退款或重复回补；处理记录可查 |
| EC10 | 切换支付 provider 或停用电商相关插件 | 在途交易、回调与退款有处理方案，历史订单可访问 |
| EC11 | 同一套源码在 Cloudflare 和 Node.js 运行上述交易故障场景 | 两种运行目标均满足约定的交易正确性与恢复要求 |
| EC12 | 管理员或 agent 尝试越权查看订单或发起退款 | API 按权限拒绝；操作结果有可追溯记录 |
| EC13 | 使用不同商家所在地和销售区域配置，切换已安装的物流适配器和配送方案 | 不修改业务核心；匹配有效配送能力与报价，按配置完成履约；不支持的组合有明确处理 |
| EC14 | 仅选择电商并构建，随后启用电商 | 自动安装用户管理，运行时联动启用并检查就绪状态；依赖未就绪时电商不进入已启用状态 |
| EC15 | 电商启用期间请求停用用户管理 | 拒绝并列出电商等已启用依赖者，保持原状态；不自动联动停用电商 |
| EC16 | 未登录或登录失效后，通过页面或直接调用 API 提交订单 | 页面引导登录，服务端拒绝创建新订单；不能只依赖前端登录拦截 |
| EC17 | 买家登录后提交其他账号 ID，或仅提交相同邮箱、手机号尝试改变购买主体 | 服务端以当前登录身份确定购买主体，拒绝以提交字段越权关联其他账号 |
| EC18 | 未登录时浏览商品、加入购物车并进入提交订单流程 | 浏览与加购可用，提交订单前引导登录；直接调用下单 API 仍需有效登录身份 |
| EC19 | 买家登录后验证并绑定新登录身份，随后换用该身份登录查询已有订单 | 解析到同一本站账号，按原有授权访问订单，订单归属与成交快照保持不变 |
| EC20 | 同一站点为 SKU 独立配置两种已开放交易币种的售价，并在兼容支付渠道下分别报价、下单和付款 | 均使用对应币种的独立售价并验证渠道，订单/支付快照及导出保留原币种和金额；不把展示换算当作交易已支持 |
| EC21 | 修改同一 SKU 的一种币种售价，再查询另一币种售价及此前已成交订单 | 另一币种售价和历史成交快照保持不变，不调用汇率自动更新其他售价，也不将缺价解释为零元或自动换算价 |
| EC22 | 站点启用人民币和美元，某 SKU 仅配置人民币售价；分别尝试以人民币和美元购买，包括直接调用下单 API | 缺少美元售价不阻止该 SKU 上架及在其他销售条件满足时以人民币购买；服务端拒绝以美元购买，不按零元或汇率换算补价 |
| EC23 | 分别创建人民币和美元订单，检查各项计价与导出，再直接调用 API 尝试向单笔订单混入另一币种的商品或费用 | 每单商品、优惠、运费、税费和总额均保留同一交易币种；服务端拒绝混合币种订单，不直接相加不同币种金额；不同订单可采用不同币种 |
| EC24 | 购物车含人民币/美元均有售价的 SKU 和仅有人民币售价的 SKU，切换到美元，并通过页面及 API 尝试结算，随后移除缺价商品或切回人民币 | 有美元售价的商品按美元独立售价重报价；缺价商品及数量保留并标记不可购，服务端阻止结算，不自动移除、零元补价或静默跳过下单；用户处理缺价后且其他销售条件满足时可结算 |
| EC25 | 匿名购物车和当前账号购物车使用相同币种，分别包含相同 SKU 的 2 件和 3 件及各自独有商品，登录前价格或库存已变化 | 登录后自动合并并保留独有商品，该 SKU 数量为 5，按当前价格和库存重新校验，不把旧报价当成交价或绕过库存限制；不得关联其他账号购物车 |
| EC26 | 登录前当前匿名购物车使用美元，账号已有购物车使用人民币，账号购物车含仅有人民币售价的商品，随后登录合并 | 合并后采用美元，同 SKU 数量相加，全部商品按美元独立售价重报价并校验库存；缺少美元售价的商品保留并阻止结算，不沿用人民币旧报价或按汇率补价，按 R70 处理缺价后才可继续 |
| EC27 | 匿名用户在同一浏览器重新打开站点；登录账号修改购物车，再在另一设备登录同一账号读取购物车，另以其他账号查询 | 在约定保存期限内，匿名购物车可在原浏览器继续使用，账号购物车由服务端保存并可在另一设备继续使用，其他账号不能读取；不承诺匿名购物车跨设备恢复或多设备实时推送，操作后仍校验价格库存 |
| EC28 | 默认配置下，分别在匿名购物车最后修改满 30 天、账号购物车最后修改满 90 天前后读取和尝试结算，期间仅浏览或刷新；另配置其他保存期限再验证 | 按各自配置及最后修改时间判定到期，仅浏览或刷新不续期；到期购物车不能沿用旧内容结算或参与登录合并，清理不影响历史订单；备份恢复保留到期信息，不因恢复重置保存期限 |
| EC29 | 两台设备读取同一 SKU 数量后先后提交不同数量，第二次修改仍基于第一次提交前的旧内容 | 按 Q68 已确认规则拒绝冲突修改，提示刷新后重新确认；不覆盖已提交数量，不把设备间数量修改当作登录合并直接相加；此项留待后续电商实施验证 |

最终验收还需确定可承载的商品和订单规模、并发量、可接受恢复时间以及支持的市场与渠道。
